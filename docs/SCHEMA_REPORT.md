## 1. 결과 요약

- 명세서의 **32개 테이블, 220개 컬럼**을 한글 이름 그대로 생성했다. (목차의 컬럼 수 합계와 일치.) 최초 명세서(30개 테이블, 204개 컬럼) 이후 사용자 결정으로 추가된 것: `인물.소개`(0020), `공개` 테이블(0021), `계정.권한`(0007), `작품.공개권한`과 `테스터` 테이블(0008, 이름은 0010 에서 `테스터`에서 변경), `방.작품_번호`·`방.버전_버전`과 1방 1게임 제약(0009)
- 빈 PostgreSQL 16 DB 에 마이그레이션 9개가 순서대로 정상 적용되고, 재실행하면 아무것도 적용하지 않는다.
- 테스트 **66개 모두 통과**.
- 제약: PK 30, UNIQUE 23, FK 61(복합 22), CHECK 27, 추가 인덱스 37, 트리거 3.
- JSONB 컬럼 9개는 내부 형식 검사 없이 생성했다.
- **확인이 필요한 항목은 8장**에 모았다. 명세서의 테이블·컬럼은 변경하지 않았다.

## 2. 파일 구성

```
db/
  migrations/
    0001_accounts.sql                 계정, 로그인세션
    0002_works.sql                    작품, 버전
    0003_phase_gimmick_library.sql    진행단계, 기믹
    0004_scenario_content.sql         제작용 콘텐츠 17개 테이블
    0005_runtime.sql                  방, 진행, 참여, 기믹실행, 투표결과, 엔딩, 획득
    0006_triggers.sql                 트리거 3개 (함수 3개)
  scripts/
    migrate.py                        마이그레이션 실행기 (표준 라이브러리 + psql)
    dump_schema_md.py                 SCHEMA_REFERENCE.md 생성기
  spec/schema_spec.xlsx               명세서 사본 (테스트가 직접 읽음)
  tests/                              테스트 4개 모듈 + 헬퍼
docs/                                 이 문서들
```

생성 순서는 FK 의존 순서를 따른다: 계정 → 작품 → 라이브러리(진행단계·기믹) → 제작용 콘텐츠 → 게임 실행 → 트리거.

## 4. 명세서에 없어 설계로 결정한 사항

명세서가 정하지 않은 부분을 아래처럼 정했다. 모두 마이그레이션 파일에 주석으로 남아 있다.

| 항목 | 결정 | 이유 |
|---|---|---|
| IDENTITY 방식 | `GENERATED ALWAYS` | 번호를 직접 지정하는 실수를 막는다. 필요하면 `OVERRIDING SYSTEM VALUE` |
| 식별자 | 모든 테이블·컬럼명을 큰따옴표로 감쌈 | `"NPC"`가 소문자로 변환되는 것을 막는다 |
| 제약·인덱스 이름 | `pk_`, `uq_`, `fk_`, `ck_`, `ix_` + 한글 | 오류 메시지에서 어느 제약인지 바로 알 수 있다 |
| ON DELETE 정책 | `DB_RULES.md` 1-7 | 제작용 콘텐츠가 삭제·수정돼도 게임 기록이 영향받지 않게, 기록 보존용 FK 는 삭제 불가 |
| FK 지원 인덱스 | 37개 추가 | PostgreSQL 은 FK 컬럼에 인덱스를 자동 생성하지 않는다 |
| 트리거 3개 | 버전 불변, 방·진행 시각 | 명세서 "특징" 칸의 자연어 규칙 중 SQL 로 구현 가능한 것. 백엔드로 옮기려면 마이그레이션 0007 로 제거 |
| 버전 불변 범위 | `시나리오`, `작품_번호`, `버전` 변경 금지 (`변경사항`은 수정 가능) | 명세서는 `시나리오`만 언급했으나, 게임이 `(작품_번호, 버전)`으로 스냅샷을 가리키므로 함께 보호 |
| 마이그레이션 실행기 | 표준 라이브러리 + `psql` | 이 환경에서 `pypi.org` 가 조직 정책으로 차단되어 psycopg·pytest 를 설치할 수 없었다 |
| 게임 실행 FK 정책 | 작품·버전·계정·방 RESTRICT, 진행 하위 기록은 진행 삭제 시 CASCADE | 기록 보존 |

명세서의 CHECK 중 아래는 **명세서 문구 그대로** 구현했고 변경하지 않았다.
`작품.최대인원 >= 최소인원`(기본값 4/4와 함께), `미디어`의 연결 대상 제약 없음, 인물 나이 등 범위 제약 없음.

## 5. 마이그레이션 적용 방법

```bash
# libpq 표준 환경변수로 접속 정보를 지정
export PGHOST=127.0.0.1 PGPORT=5432 PGUSER=postgres PGPASSWORD=...

createdb murder_mystery
python3 db/scripts/migrate.py --dbname murder_mystery       # 9개 파일을 순서대로 적용
python3 db/scripts/dump_schema_md.py --dbname murder_mystery > docs/SCHEMA_REFERENCE.md
```

- 실행기는 파일마다 하나의 트랜잭션으로 적용하고, 실패하면 그 파일 전체를 롤백하고 중단한다.
- 적용 이력과 SHA-256 체크섬은 `schema_migrations` 테이블에 저장되며, **이미 적용된 파일을 수정하면 실행을 거부한다.** 변경은 새 번호의 파일로 추가한다.
- 이 실행기는 임시 도구이다. 백엔드 단계에서 다른 마이그레이션 도구로 바꾸더라도 SQL 파일은 그대로 쓸 수 있다.

## 6. 테스트 결과

실행: `cd db/tests && python3 -m unittest discover -s . -p 'test_*.py'`
환경: PostgreSQL 16.15, Python 3.13 (표준 `unittest`, pytest 로도 실행 가능한 형식). 전체 약 98~128초, **66개 통과 / 실패 0** (0007 반영 후에도 동일).
테스트마다 임시 DB 를 만들어 마이그레이션을 처음부터 적용하고 끝나면 삭제한다 (`CREATEDB` 권한 필요).

| 모듈 | 테스트 수 | 검증 내용 |
|---|---|---|
| `test_migrations.py` | 7 | 빈 DB 에 전체 적용, 30개 테이블 생성, 재실행 멱등, 실패 파일 전체 롤백, 적용된 파일 수정 감지, 잘못된 파일명 거부, `"NPC"` 대소문자 |
| `test_spec_conformance.py` | 7 | **엑셀을 직접 읽어** 컬럼 이름·순서·타입·NULL·기본값·IDENTITY, PK/단일·복합 FK/단일·복합 UNIQUE/CHECK 개수를 양방향으로 대조(명세서에 없는 FK·UNIQUE 도 검출), FK 타입 일치(61개), FK 대상이 이름 규칙과 일치, **복합 FK 대상이 PK/UNIQUE 와 정확히 일치**, 모든 FK 에 지원 인덱스 존재 |
| `test_integrity.py` | 29 | CHECK 위반 거부(상태·환경·만료·인원·순서·진행시간·유형), 복합 UNIQUE 위반, **작품 간 교차 참조 거부 19가지**, nullable 참조의 NULL 허용, "정확히 1개" 규칙(0·2·3개 거부), 확정 버전이 없으면 게임 생성 불가, 다른 작품의 버전 거부, 한 방에서 여러 판 순차 진행 |
| `test_isolation_and_triggers.py` | 23 | **제작용 콘텐츠 전체 삭제·수정 시 게임 기록 불변(해시 비교)**, 게임 테이블이 콘텐츠 테이블을 참조하지 않음, 새 버전이 구 버전 게임에 영향 없음, 게임이 있는 작품 삭제 거부, 삭제 정책 전체, 버전 불변 트리거, 방·진행 시각 트리거, **JSONB 9개 컬럼이 어떤 JSON 값도 받고 JSONB 대상 CHECK 가 없음** |

테스트가 실제로 불일치를 잡는지 확인하려고, 마이그레이션을 일부러 망가뜨린 사본으로 `test_spec_conformance.py`를 실행했다.
기본값 변경, 컬럼 타입 변경(INTEGER→BIGINT), 복합 UNIQUE 제거, CHECK 제거, FK 인덱스 제거가 **모두 검출**되었다. 복합 FK 대상 UNIQUE 를 제거한 경우는 마이그레이션 단계에서 FK 생성이 거부되었다.

**정정:** 작업 중 "작품 삭제의 CASCADE 도중 `RESTRICT`가 먼저 걸려 실패할 수 있다"고 보고 작품 내부 참조를 `NO ACTION`으로 바꿨다가, 직접 실험해 보니 PostgreSQL 16에서는 `RESTRICT`로도 정상 삭제되어 가설이 입증되지 않았다. 의도가 분명한 `RESTRICT`로 되돌렸고, 같은 상황을 잡는 회귀 테스트(`test_deleting_work_without_games_removes_all_its_content_and_versions`)는 그대로 둔다.

**테스트하지 않은 것**
- PostgreSQL 16 외의 버전.
- Docker/docker-compose (이 환경에서 Docker 데몬을 쓰지 않았고 해당 파일은 만들지 않았다).
- 동시 요청 환경(경쟁 조건). 단일 연결 순차 실행만 확인했다.
- 대용량 데이터의 인덱스 성능.

## 7. 향후 백엔드에서 구현해야 할 항목

전체 목록(B1~B33)은 `DB_RULES.md` 2장. 핵심만 요약한다.

- **스냅샷 참조 검증**: JSONB 를 가리키는 모든 `*_순서` 컬럼 (진행, 참여, 획득, 기믹실행, 투표결과, 엔딩)
- **확정 흐름**: 스냅샷 직렬화(라이브러리 사본 포함), 버전 문자열 규칙, `최신버전`·`수정일시` 갱신
- **최대인원 자동 갱신**: `최대인원 >= 최소인원` CHECK 와 기본값 4/4 때문에 인물을 추가하는 도중 갱신이 거부될 수 있다
- **방 자동 종료**, 방·진행 상태 일관성, 동시 진행 1개 제한
- **획득 양도** 처리와 중복 보유 방지
- **정보 노출 제어**: 스냅샷에 범인·비밀이 들어 있으므로 플레이어별 필터링 필수
- **JSONB 내부 형식 정의와 검증** (`JSONB_COLUMNS.md`)

## 8. 확인 요청

명세서의 테이블·컬럼은 변경하지 않았다. 아래는 모호하거나 결정이 필요해서 **기본 동작을 적용했거나 미적용으로 둔** 항목이다.

| # | 항목 | 현재 처리 | 확인할 내용 |
|---|---|---|---|
| 1 | **기믹실행의 UNIQUE** — 명세서는 이 제약을 `실행여부` 행에 적었으나 컬럼 목록은 `(진행_번호, 기믹적용_순서)` | 두 컬럼의 복합 UNIQUE 로 해석해 적용 | 해석이 맞는지 |
