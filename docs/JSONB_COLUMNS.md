# JSONB 컬럼: 형식이 필요한 항목과 향후 검증 관계

## 현재 상태

- 명세서에 정의된 JSONB 컬럼 **9개**를 그대로 생성했다. (이전 대화에서 조건·결과·규칙류를 "7개"라고 한 것은 세는 과정의 오류였다. 실제로는 그 부류가 8개이고 `버전.시나리오`를 더해 9개이다.)
- **내부 필드·규칙은 임의로 확정하지 않았다.** JSONB 형식을 검사하는 CHECK 는 하나도 없고, 테스트(`TestJsonbColumnsAreFreeForm`)가 다음을 확인한다.
  - 객체, 배열, 문자열, 숫자, 불리언, JSON `null` 등 어떤 JSON 값이든 저장된다.
  - SQL NULL 은 명세서에서 NULL 불가인 컬럼에서만 거부된다.
  - JSONB 컬럼을 대상으로 하는 CHECK 제약이 없다.
- 내부 구조는 이후 백엔드 개발 단계에서 JSON Schema 또는 Pydantic 모델로 정의할 예정이다.

## 1. 컬럼 목록

| # | 컬럼 | NULL | 명세서 설명 | 성격 |
|---|---|---|---|---|
| 1 | `버전.시나리오` | 불가 | 해당 버전의 전체 시나리오 데이터 저장 (확정 후 변경하지 않음) | **불변 스냅샷** |
| 2 | `진행단계.규칙` | 불가 | 진행단계 규칙 (게임 엔진 해석용 구조화 데이터) | 라이브러리 (공통/제작자) |
| 3 | `기믹.조건` | 불가 | 기믹 조건 (게임 엔진 해석용) | 라이브러리 |
| 4 | `기믹.결과` | 불가 | 조건 충족 시 실행 결과 (게임 엔진 해석용) | 라이브러리 |
| 5 | `엔딩분기.조건` | 불가 | 엔딩 진입 조건 (게임 엔진 해석용) | 작품 |
| 6 | `후일담.조건` | 가능 | 후일담 적용 조건 (게임 엔진 해석용) | 작품 |

## 2. 형식이 필요한 정보 (정의해야 할 질문)

### 2-1. `버전.시나리오` — 확정된 작품 전체의 불변 스냅샷

게임은 이 스냅샷을 기준으로 동작하고, 제작용 콘텐츠 테이블이 이후 바뀌거나 삭제되어도 영향을 받지 않아야 한다. 따라서 스냅샷은 **그 자체로 완결되어야 한다.**

스냅샷에 들어가야 하는 것 (이 목록은 게임 동작에 필요한 정보를 기준으로 한 정리이며, 실제 구조는 Pydantic 모델 정의 단계에서 확정된다):

| 구분 | 내용 | 이유 |
|---|---|---|
| 작품 메타 | 제목, 시놉시스, 장르, 최소·최대인원, 예상시간 | 게임 시작·표시에 필요 |
| 제작용 콘텐츠 17개 테이블 | 진행순서, 진행구성, 기믹적용, 인물, 관계, 장소, 단서, 증언, 조합, 조합재료, 사건, 사건설명, 엔딩분기, 후일담, 타임라인, 투표, 미디어 | 게임이 직접 읽는 데이터 |
| **라이브러리 항목의 사본** | `진행구성`이 가리키는 `진행단계`(이름·규칙·설명), `기믹적용`이 가리키는 `기믹`(이름·설명·조건·결과) | 이 항목들은 DB 에서 FK 로 참조되지 않는다. 사본이 없으면 라이브러리 항목이 수정·삭제될 때 과거 게임을 재현할 수 없다 |
| 미디어 파일 참조 | `미디어.경로` | 파일 자체는 DB 밖에 있다. 파일이 삭제·교체되면 스냅샷이 불변이어도 게임이 깨진다 |

스냅샷 내부 번호의 의미:

- `참여.인물_순서`, `획득.단서_순서`, `진행.진행순서_순서`, `기믹실행.기믹적용_순서`, `투표결과.투표_순서`, `엔딩.엔딩분기_순서` 등은 **스냅샷 안의 `순서` 값**을 가리킨다.
- 따라서 스냅샷 안의 각 항목은 제작 시점의 `순서` 값을 그대로 유지해야 하고, 확정 후에는 번호를 바꿀 수 없다.

**기존 버전과의 호환성 (결정이 필요한 항목)**

| 항목 | 질문 |
|---|---|
| 스키마 버전 표기 | 스냅샷 형식이 바뀔 때 구 형식을 어떻게 구분할 것인가. 스냅샷은 불변이므로 DB 컬럼 추가 없이 JSONB 최상위에 형식 버전 값을 둘지, 별도 컬럼을 추가할지(명세서 변경이므로 확인 필요) 결정해야 한다. |
| 구 버전 읽기 | 이미 확정된 구 형식 스냅샷을 새 코드가 읽을 때, 읽는 시점에 변환할지 구 형식 모델을 계속 유지할지 정해야 한다. 불변 원칙상 저장된 스냅샷 자체를 수정하는 마이그레이션은 하지 않는 것이 전제이다. |
| 필드 변경 규칙 | 새 필드는 선택·기본값으로 추가하고, 기존 필드의 삭제나 의미 변경은 새 형식 버전으로만 허용하는 식의 규칙이 필요하다. |
| 진행 중인 게임 | 게임이 진행되는 동안 형식이 바뀌어도 그 게임은 시작 시점 버전의 형식으로 끝까지 처리되어야 한다. |
| `버전.버전` 문자열 | TEXT 이므로 `1.9`와 `1.10`의 순서를 문자열 비교로 판단하면 안 된다. 비교·증가 규칙을 정해야 한다. |
| 크기 | 미디어는 경로만 포함하므로 크기 문제는 작지만, 인물 서사·증언 등 긴 텍스트가 많은 작품의 스냅샷 크기는 확인되지 않았다. |

### 2-2. 조건류 — `기믹.조건`, `엔딩분기.조건`, `후일담.조건`, `미디어.조건`

| 정의가 필요한 것 | 비고 |
|---|---|
| 공통 조건 표현식 문법 (비교, 논리 연산, 집합 포함 등) | 4개 컬럼이 같은 문법을 쓸지, 컬럼별로 다른지 |
| 조건이 읽을 수 있는 상태 값 | 예상 후보: 단서·증언·조합 보유 여부(`획득.보유여부`), 투표 결과(`투표결과.선택`), 기믹 실행 여부(`기믹실행.실행여부`), 현재 진행 순서(`진행.진행순서_순서`), 참여자의 배역 |
| 참조 방식 | 스냅샷 안의 인물·단서·증언·조합·투표 등을 `순서` 번호로 가리키게 될 것이다 |
| `후일담.조건` ↔ `후일담.인물_순서` | 조건이 NULL 일 때와 인물_순서가 NULL 일 때의 의미 조합을 정의해야 한다 |
| `미디어.조건` | 명세서에 "엔진 규격 확정 필요"로 이미 표시됨 |

### 2-3. 결과류 — `기믹.결과`, `기믹실행.결과`

| 정의가 필요한 것 | 비고 |
|---|---|
| 실행 가능한 동작의 종류 | 예: 단서 공개, 미디어 표시, 진행 단계 변경 — 목록 확정 필요 |
| `기믹실행.결과`와 `기믹.결과`의 관계 | 계획된 결과와 실제 처리 결과(성공·실패·대상)를 같은 구조로 쓸지 |

### 2-4. 규칙류 — `진행단계.규칙`, `투표.규칙`

| 정의가 필요한 것 | 비고 |
|---|---|
| 진행 단계에서 허용되는 행동, 시간 제한 등 | `진행순서.진행시간`(분)과 중복되는 항목이 있는지 |
| 투표의 선택지 종류 | 인물 선택, 예/아니오 등. `투표결과.선택`(TEXT)이 선택지를 어떻게 표현할지 |
| 집계·동률 처리, 투표 대상 범위 | |

## 3. 명세서에서 발견된 JSONB 관련 모호점 (확인 요청)

**기믹을 작품 대상에 연결하는 방법이 없다.** `기믹`은 작품과 무관한 라이브러리 항목이고(`작품_번호` 없음) `기믹.조건`/`결과`는 특정 인물·단서·투표 등을 가리킬 필요가 있을 것이다. 그런데 `기믹적용`은 `(작품_번호, 순서, 기믹_번호, 진행순서_순서)`만 가지고 있어 "이 작품의 어떤 단서에 이 기믹을 적용하는지"를 저장할 곳이 없다. 기믹이 대상 지정 없이 일반 규칙(예: 모든 참여자 대상)만 표현하도록 의도된 것인지, 별도 값(예: 적용 인자)이 필요한지 확인이 필요하다. 이 부분은 테이블·컬럼을 임의로 추가하지 않았다.

## 4. 향후 검증해야 할 관계

JSONB 내부 형식이 정해지면 다음 관계를 검증(Pydantic/JSON Schema + 백엔드)해야 한다. DB 는 이 관계를 검증할 수 없다.

| # | 관계 | 검증 시점 |
|---|---|---|
| J1 | 스냅샷 안의 모든 `*_순서` 참조가 같은 스냅샷 안에 존재하는 항목을 가리킨다 (인물·장소·단서·증언·조합·사건·진행순서·투표) | 스냅샷 생성(확정) 시 |
| J2 | 제작용 콘텐츠 → 스냅샷 직렬화가 누락·중복 없이 이루어진다 (행 수, `순서` 유일성) | 확정 시 |
| J3 | 스냅샷에 포함된 기믹·진행단계 사본이 확정 시점의 라이브러리 값과 같다 | 확정 시 |
| J4 | `조건` 표현식이 참조하는 항목(단서·투표·기믹 등)이 스냅샷에 존재한다 | 저장·확정 시 |
| J5 | `투표.규칙`의 선택지와 `투표결과.선택` 값이 대응한다 | 투표 제출 시 |
| J6 | `기믹실행.결과`가 해당 `기믹.결과`의 허용 형식을 따른다 | 기믹 실행 시 |
| J7 | `엔딩분기.조건`, `후일담.조건`이 평가 가능하고, 모든 가능한 진행에서 최소 하나의 엔딩이 선택된다 | 확정 시 |
| J8 | `진행.버전_버전`의 스냅샷 형식 버전을 지원하는 코드가 있다 | 게임 시작 시 |
| J9 | 확정 버전이 참조하는 미디어 파일이 저장소에 존재하고 이후 변경되지 않는다 | 확정 시 / 정기 점검 |
| J10 | 클라이언트에 내려보내는 스냅샷 일부에 범인·비밀 같은 비공개 정보가 포함되지 않는다 | 모든 응답 |

## 5. 결정이 필요한 항목 요약

1. 스냅샷 형식 버전을 JSONB 안에 둘지, 컬럼을 추가할지
2. 기믹에 작품별 대상을 연결하는 방법 (3장)
3. 조건 표현식 문법을 4개 조건 컬럼이 공유하는지
4. 구 형식 스냅샷을 읽을 때의 처리 방식
5. 미디어 파일의 불변 보장 방법
