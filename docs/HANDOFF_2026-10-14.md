# 인수인계 — 머더미스터리 플랫폼 (2026-10-14)

이 문서는 새 세션(Claude Code 등)이 **대화 기록 없이** 이어서 작업할 수 있도록 쓴 것이다.
파일에 이미 있는 내용은 요약하고 위치를 적었으며, **대화에서만 정해졌던 내용**을 이 문서에 처음 기록한다.
확정과 미결정을 구분해 적었다. "미결정"을 임의로 확정하지 말고 사용자에게 먼저 물어야 한다.

---

## 1. 프로젝트

- **무엇을**: 머더미스터리 게임 시나리오를 제작하고, 완성된 작품을 같은 사이트에서 함께 플레이하는 웹 플랫폼.
- **구성**: 제작 툴은 **PC 전용**, 플레이는 **PC·모바일 모두**. 음성 대화는 **Discord 병행**(사이트에 음성 기능 없음).
- **추후**: 3D 작업 연동을 검토 중이다 (어떤 3D인지는 정해지지 않음).
- **개발자**: 사용자 1명. 직업훈련 수업 프로젝트 발표가 대화 시점에 **5일 남아** 있었다(정확한 날짜는 확인하지 못함). 다만 발표와 별개로 **이 프로젝트를 제대로 완성하고 싶어 한다**고 밝혔다. 그래서 스키마도 상세하게 설계했다.
- **사용자 상황**: Python, PostgreSQL, Docker, pgAdmin4 사용 경험이 있다. JavaScript/React는 직접 작성한 경험이 아니라 Claude로 만들어 본 정도라고 밝혔다. 사용자가 다른 프로젝트 후 받은 자기평가(AI가 작성)에서는 코드 직접 읽기·자동 테스트가 약하고 설계 결정·컨텍스트 관리·AI 출력 검증이 강한 것으로 나왔다. 이 평가는 다른 프로젝트 기록에 근거한 것이라 이 프로젝트에 그대로 적용된다고 단정할 수는 없다.

## 2. 현재 상태

**완료: 데이터베이스 구축 단계** (프론트엔드, API, 게임 엔진은 **아직 없음**)

| 항목 | 상태 |
|---|---|
| 테이블 30개 / 컬럼 204개 | 명세서 그대로 한글 이름으로 생성 |
| 마이그레이션 | `db/migrations/0001~0006`, 빈 PostgreSQL 16에 정상 적용 |
| 테스트 | 66개 통과 (`db/tests`) |
| 문서 | `docs/SCHEMA_REPORT.md`, `DB_RULES.md`, `JSONB_COLUMNS.md`, `SCHEMA_REFERENCE.md` |

먼저 읽을 순서: 이 문서 → `docs/SCHEMA_REPORT.md`(구성·결정·확인 요청) → `docs/DB_RULES.md`(백엔드 규칙) → `docs/JSONB_COLUMNS.md`.

### 실행

```bash
export PGHOST=127.0.0.1 PGPORT=5432 PGUSER=postgres PGPASSWORD=...
createdb murder_mystery
python3 db/scripts/migrate.py --dbname murder_mystery
cd db/tests && python3 -m unittest discover -s . -p 'test_*.py'     # 약 100초, CREATEDB 권한 필요
```

- 실행기와 테스트는 `psql` 명령을 직접 호출한다. `psql`이 PATH에 있어야 한다.
- 마이그레이션 실행기는 표준 라이브러리 + `psql`만 쓰는 임시 도구이다 (개발 환경에서 `pypi.org`가 차단되어 psycopg·pytest를 설치할 수 없었다). 테스트는 `unittest` 형식이며 pytest로도 실행된다.
- Docker/docker-compose 파일은 **만들지 않았다**.

### 주의

- **적용된 마이그레이션 파일은 수정하지 않는다.** 체크섬이 달라지면 실행기가 중단한다. 변경은 `0007_*.sql` 같은 새 파일로 추가한다.
- 모든 식별자는 큰따옴표로 감싼다. 특히 `인물."NPC"`는 따옴표가 없으면 `npc`가 된다.
- 번호 컬럼은 `GENERATED ALWAYS AS IDENTITY`라서 번호를 직접 넣으려면 `OVERRIDING SYSTEM VALUE`가 필요하다.

## 3. 확정된 결정

### 3-1. 기술 스택 (사용자가 아래 표를 본 직후 "리액트로 가자"고 답했다. 명시적으로 확정한 것은 React뿐이고, 나머지 항목에는 이의가 없었던 상태이다)

| 영역 | 선택 |
|---|---|
| DB | PostgreSQL (관리 도구 pgAdmin4) |
| 스키마 관리 | SQL 마이그레이션 파일을 프로젝트에 보관 (ORM 미사용 방향) |
| 백엔드 | Python + FastAPI + Pydantic, DB 접근은 psycopg 3로 SQL 직접 작성 |
| 프론트엔드 | React + Vite |
| 타입 공유 | FastAPI의 API 명세(OpenAPI)에서 프론트 타입 자동 생성 |
| 실시간 | **폴링(2~3초)으로 시작**, 필요하면 SSE로 교체 (WebSocket은 쓰지 않음) |
| 파일 저장 | 서버 로컬 디스크 (`미디어.경로`에 경로 저장) |
| 테스트 | pytest, 특히 DB 제약 위반과 서버 규칙 |
| 배포 | Docker Compose (앱 + PostgreSQL) |
| 3D(추후) | Three.js를 React 안에 통합 |

폴링을 고른 이유: 모든 통신이 일반 HTTP가 되어 API 명세에 전부 포함되므로 타입 자동 생성이 끊기지 않는다. 머더미스터리는 진행이 느려 2~3초 지연이 문제가 될지는 **실제 플레이로 확인해야 한다**(검증된 것이 아니다).

### 3-2. 개발 순서

백엔드 전체를 끝낸 뒤 프론트를 붙이지 않고, 기반을 먼저 만든 뒤 **기능 단위로 "API → pytest → 화면"을 묶어서** 진행한다.

1. DB 스키마 (완료)
2. FastAPI 골격과 DB 연결
3. 계정·로그인 API (`작품.계정_번호`가 NOT NULL이라 모든 기능의 전제)
4. React 골격과 로그인 화면으로 백엔드 연결 확인
5. 기능 단위 반복: 작품 → 인물·장소·단서·증언 편집 → 방 → 플레이 화면

### 3-3. 비밀번호 (유력안, 명시적으로 확정하지는 않음)

Argon2 계열이 유력하다. 사용자가 다른 작업에서 `pwdlib`(Argon2)를 써 본 적이 있다. `argon2-cffi`를 감싼 상위 라이브러리로 알고 있으나 이 프로젝트에서 확인하지는 않았다. 저장은 `계정.패스워드`(TEXT) 한 컬럼으로 충분하다. `로그인세션.토큰`은 추측 불가능한 무작위 값이므로 SHA-256 같은 빠른 해시를 쓸 수 있다 (솔트 있는 해시는 UNIQUE 조회가 불가능).

### 3-4. DB 설계에서 사용자가 확정한 것

| 항목 | 확정 내용 |
|---|---|
| "정확히 하나" CHECK | `조합재료`, `엔딩`, `획득`은 모두 **정확히 1개** (`num_nonnulls = 1`) |
| 인물.NPC | TRUE = NPC = 플레이 불가, 기본값 FALSE. 피해자나 서사가 필요한 비플레이 인물에 사용 |
| 방과 진행 | ~~한 방에서 게임을 끝낸 뒤 추가로 더 플레이할 수 있다 (1방 N판)~~ → **변경(2026-10-14): 1방 1게임.** 방 생성 시 작품을 고르고 확정된 최신 버전이 자동으로 정해진다 (마이그레이션 0009) |
| 대기실 인원 | 시작 전 입장자는 DB에 기록하지 않는다. 서버 재시작 시 대기실 상태가 사라져도 된다 |
| 서버 재시작 | 극단적 상황으로 보고 지금은 고려하지 않는다 |
| 최대인원 자동 갱신 | **백엔드**에서 한다 (NPC가 아닌 인물 수) |
| 방 자동 종료 | **백엔드**에서 한다 |
| 범인 | 일반적인 시나리오는 1명. 다른 특징이 필요하면 다른 컬럼을 쓴다 |
| JSONB 내부 구조 | **DB 생성 후에 정한다.** 백엔드 단계에서 JSON Schema 또는 Pydantic으로 정의할 예정. 임의 확정 금지 |

## 4. 미결정 · 확인 요청

**사용자의 결정 없이 기본 동작을 적용했거나 미적용으로 둔 항목이다.** 상세는 `docs/SCHEMA_REPORT.md` 8장.

| # | 항목 | 현재 처리 |
|---|---|---|
| 1 | 기믹실행의 UNIQUE 해석 (`실행여부` 행에 적혔으나 컬럼 목록은 `진행_번호, 기믹적용_순서`) | 후자의 복합 UNIQUE로 해석해 적용 |
| 2 | 작품 삭제 처리 (삭제 상태 값이 없음. 게임이 있는 작품은 DB가 삭제 거부) | 삭제 거부 |
| 3 | 기믹을 작품 대상에 연결하는 방법 (`기믹적용`에 인자 저장 위치 없음) | 변경하지 않음 |
| 4 | 한 방의 동시 진행 1개 제한 | **해결(2026-10-14)**: 1방 1게임으로 바뀌어 DB(UNIQUE)가 보장 |
| 5 | 하위 테이블 `작품_번호`와 `진행.작품_번호`의 불일치 방지 | DB에서 막지 않음. 사용자가 **보류** ("고민해볼게") |
| 6 | 획득의 양도 처리 (시각·양도자 컬럼 없음, 보유 중복 제약 없음) | 명세서 그대로. 사용자가 **점검하겠다고 함** |
| 7 | `인물.NPC` 컬럼 설명 문구 (TRUE의 의미 명시) | 엑셀 문서 수정은 사용자 몫 |
| 8 | 인원 CHECK(`최대 >= 최소`, 기본 4/4)와 자동 갱신의 충돌 | 명세서 그대로. 백엔드에서 갱신 순서·0명 처리 필요 (`DB_RULES.md` B5) |
| 9 | 스냅샷 형식 버전을 JSONB 안에 둘지 컬럼으로 둘지 | 미결정 |
| 10 | 개발 범위 축소안 (아래) | 제안만 했고 사용자가 명시적으로 채택하지 않음 |
| 11 | TypeScript 사용 여부 | 설명만 했고 사용자는 "JS와 똑같다"고 답함. 미결정 |
| 12 | 3D 연동의 구체적 내용 | 미정 |

**개발 범위 축소안(제안, 미채택)**: 5일 안에 전체를 혼자 완성하기는 어렵다고 평가했다 (확신은 아님). 최소 범위는 계정/로그인, 작품 기본정보·인물·장소·단서·증언·진행순서·투표·엔딩 편집, 방 생성/입장, 단서 열람·투표·엔딩 표시이다. 조합, 기믹, 미디어, 관계, 타임라인, 사건설명, 후일담, 획득 양도는 이후로 미루는 구성이다.

## 5. 다음 작업 시 규칙 (사용자가 명시한 작업 지침)

DB 구축 단계에서 사용자가 준 지침 중 이후에도 유효한 것:

1. **명세서(`db/spec/schema_spec.xlsx`)를 기준으로 한다.** 테이블·컬럼은 한글 이름을 유지한다.
2. **명세서에 오류나 모호함이 있으면 테이블·컬럼을 임의로 바꾸지 말고 먼저 확인을 요청한다.**
3. **제작용 콘텐츠 테이블과 게임 실행 테이블을 구분한다.** 게임은 `진행`에 연결된 확정 버전의 `버전.시나리오` JSONB를 기준으로 동작한다. 제작용 콘텐츠의 수정·삭제가 이전 게임과 기록에 영향을 주면 안 된다.
4. **DB에서 강제할 규칙과 백엔드에서 검증할 규칙을 구분해 문서화한다.** SQL로 어려운 규칙도 누락하지 않는다 (`DB_RULES.md`).
5. **JSONB 내부 구조를 임의로 확정하지 않는다.** 필요한 형식과 검증 관계는 별도 문서로 정리한다. `버전.시나리오`는 확정된 작품의 **불변 스냅샷**이며 기존 버전과의 호환성을 고려해야 한다.
6. 마이그레이션으로 테이블을 만들고, 빈 DB에서 전부 적용되는지 테스트한다.

## 6. 백엔드 구현 시 반드시 주의할 점

(상세는 `docs/DB_RULES.md` 2장)

- **정보 노출**: 스냅샷에 범인·비밀이 모두 들어 있다. 클라이언트에 전체를 내려보내면 안 되고 서버가 플레이어별로 필터링해야 한다.
- **스냅샷 참조 검증**: `참여.인물_순서`, `진행.진행순서_순서`, `획득.*_순서`, `기믹실행.기믹적용_순서`, `투표결과.투표_순서`, `엔딩.*_순서`는 DB가 검증하지 못한다.
- **스냅샷은 자체 완결적이어야 한다**: 기믹·진행단계 정의의 사본과 미디어 파일 참조를 포함해야 라이브러리 항목이 바뀌거나 삭제돼도 과거 게임을 재현할 수 있다. 미디어 파일 자체도 확정 후 삭제·교체하면 안 된다.
- **확정 후 `순서` 번호 변경 금지**: 게임 기록이 스냅샷 안의 번호로 항목을 가리킨다.
- **게임이 있는 작품·확정 버전·기록이 있는 계정은 DB가 삭제를 거부한다.** 탈퇴는 `상태='탈퇴'`로 처리한다.
- **트리거 3개가 DB에 있다**: 버전 스냅샷 불변, 방·진행의 시각 기록. 백엔드로 옮기려면 새 마이그레이션으로 제거해야 한다.

## 7. 이 작업 중에 바로잡은 사항 (같은 오류를 반복하지 않기 위해)

- JSONB 컬럼은 **9개**이다 (대화 중에 조건·결과·규칙류를 7개라고 잘못 말했다).
- 작품 삭제 시 CASCADE와 RESTRICT가 충돌한다는 가설은 **PostgreSQL 16에서 입증되지 않았다.** 작품 내부 참조는 RESTRICT를 사용하며, 회귀 테스트가 있다.
- 사용자가 JavaScript를 안다고 가정하고 한 평가("React 학습 부담이 작다")는 철회되었다. 사용자는 JS를 직접 쓰지 못한다.
- 폴링이 WebSocket보다 낫다는 뜻이 아니다. 실시간 방식을 단순화해 타입 자동 생성 범위를 넓히려는 선택이다.

## 8. 테스트하지 않은 것

PostgreSQL 16 외의 버전 / Docker / 동시 요청(경쟁 조건) / 대용량 인덱스 성능 / Windows 환경.
