# 제작 환경(편집기) 설계 초안 (2026-10-15)

**상태: 초안. 사용자 확인 전.** 아래에서 `사용자`로 표시한 것만 사용자가 말한 내용이고, `해석`·`제안`은 제가 정리한 것이라 틀릴 수 있다.
이 문서는 화면 배치가 아니라 **제작자가 무엇을 할 수 있어야 하는지**와 **제작 요소가 어떻게 연결되는지**를 먼저 정하기 위한 것이다.
(`ENGINE_DESIGN.md`의 1-7 "작업공간 구현"은 이 문서의 방향과 맞지 않아 재검토 대상이다.)

## 0. 지금 구현이 어긋난 이유

2026-10-15에 만든 작업공간은 **DB 테이블마다 목록+입력 양식을 붙인 것**이다(`backend/app/content.py` 명세 하나로 모든 테이블의 API와 양식을 만든다).
이는 "저장 구조를 화면에 노출한 도구"이며, 제작자가 **새로운 요소·규칙·기믹을 정의**하는 환경이 아니다. 사용자 지적(2026-10-15)이 맞다.

## 1. 사용자가 밝힌 요구

- (사용자) 장소, 단서, 캐릭터, 기믹, 진행단계 등은 **독립적으로 제작**할 수 있어야 하고, **필요한 시점에 서로 연결**할 수 있어야 한다.
- (사용자) 제작 순서는 자유. 작품 이름·시놉시스부터 쓸 필요가 없다. 이름조차 나중에 바뀐다. (빈 작업공간에서 원하는 것부터)
- (사용자) 정해진 기능을 조합하는 것을 넘어, 제작자가 **새로운 규칙과 기믹, 나아가 새로운 기능까지 정의**할 수 있는 구조.
- (사용자) 쏘빅은 참고 사례일 뿐 모방하지 않는다. DB 구조를 화면에 그대로 노출하지 않는다.
- (사용자) 화면을 부분 수정하지 말고, **제작자가 수행할 작업과 요소 간 연결**부터 정리한 뒤 편집기 구조를 다시 설계한다.
- (사용자, 이전 결정) 기믹의 본체는 스크립트(파이썬 문법, 영어 키워드, 자체 해석기), 한글 설명 보기, AI는 프롬프트 복사·붙여넣기, 사람마다 다른 단서·활성 조건·비활성 클릭 이벤트 등 → `ENGINE_DESIGN.md` 1-4.

## 2. 제작자가 할 수 있어야 하는 작업 (해석)

| 작업 | 뜻 | 비고 |
|---|---|---|
| 만들기 | 요소를 **다른 요소 없이** 하나 만든다 | 필수 입력은 최소(이름조차 나중에) |
| 연결하기 | 두 요소를 잇는다 (단서→장소, 기믹→페이즈 등) | **연결하는 자리에서 새 요소를 바로 만들 수도** 있어야 한다(해석) |
| 연결 끊기·바꾸기 | 잇던 것을 풀거나 다른 요소로 교체 | 끊으면 어디에 영향이 있는지 보여야 한다(해석) |
| 이름·내용 바꾸기 | 만든 뒤 언제든 | 참조가 깨지지 않아야 한다 |
| 삭제 | 요소를 지운다 | 다른 요소가 쓰는 중이면 그 목록을 보여 준다(해석) |
| 정의하기 | **새 종류의 규칙·기믹·명령·(변수·태그)를 직접 만든다** | 아래 4. 범위가 핵심 질문 |
| 재사용 | 만든 기믹·진행단계를 여러 작품에서 쓴다 (버전·변경내역) | 이미 있음(라이브러리) |
| 시험하기 | 만든 것이 동작하는지 미리 본다 | **미결정**: 모의 실행·한글 설명 보기·시험 방 |
| 확정하기 | 검증 후 한 버전으로 굳힌다 | 검증은 만드는 도중이 아니라 이때(사용자 결정) |

## 3. 제작 요소와 연결 (해석)

제작 요소 = 제작자가 만들고 이름 붙이는 대상. 연결 = 한 요소가 다른 요소를 가리키는 관계.

### 3-1. 요소
인물(캐릭터), 장소, 단서, 증언, 조합, 사건·사건 상세, 타임라인, 자료(긴 글), 미디어, 관계, 투표, 엔딩 분기, 후일담, 페이즈, 진행단계(라이브러리), 기믹(라이브러리), 변수, 태그(지식), (정의한 새 요소).

### 3-2. 연결 (지금 스키마에 있는 것 = ●, 없는 것 = ○)
| 연결 | 방향 | 상태 |
|---|---|---|
| 장소 ⊃ 장소 (상위) | 장소→장소 | ● |
| 단서 → 관련 인물 / 장소 | 한 개씩 | ● (여럿 불가) |
| 증언 → 인물 / 장소 | 한 개씩 | ● |
| 조합 ⇐ 재료(단서·증언·조합) | 조합 재료 행 | ● |
| 사건 상세 → 피해자(인물) | | ● |
| 관계: 인물↔인물 | | ● |
| 투표 → 페이즈 | 한 개 | ● |
| 페이즈 ⊃ 진행단계 | 여러 개 | ● |
| 페이즈 ⊃ 기믹 | 여러 개 | ● |
| 기믹 → 단서·장소·인물·자료·변수·태그 (스크립트가 참조) | 스크립트 안에서 | ○ (참조 기록 없음) |
| 장소 ⊃ 단서 (그 장소에서 얻는 단서) | 조사가 쓰는 핵심 연결 | △ 단서→장소 칼럼 하나로만 |
| 진행단계·기믹의 작품별 설정값 | 사용처별 칸 | ○ |
| 인물 ↔ 지식 태그, 단서 ↔ 태그 | | ○ |
| 변수 (이름·자료형·초기값·열람 권한) | | ○ |
| 엔딩·후일담 조건이 읽는 요소 | 조건 안에서 | ○ |

## 4. "새로운 기능을 정의한다"의 범위 (핵심 질문, 해석)

"새로운 기능"이 어디까지인지에 따라 구조가 완전히 달라진다. 가능한 층을 나눠 보면:

| 층 | 제작자가 정의하는 것 | 이미 정한 것 |
|---|---|---|
| L1 속성 | 변수, 지식 태그, 요소에 붙이는 사용자 속성 | 변수는 필요하다고만 정함(`ENGINE_DESIGN` 3) |
| L2 규칙·기믹·명령 | 스크립트로 조건·행동·새 명령(함수) 작성 | **정함**: 파이썬 문법 스크립트, 자체 해석기, 한글 설명 보기 |
| L3 진행단계(모듈) | 새 종류의 단계(예: 쪽지, 점수판)를 정의하고 설정 패널을 가진다 | 정하지 않음 (쏘빅의 모듈에 해당) |
| L4 화면 | 서버가 화면을 JSON으로 설명, 클라이언트는 고정 부품 → 부품 조합 → 3D, 격리된 사용자 정의 화면 | 방향만 정함(`ENGINE_DESIGN` 2, 사용자 미확정) |
| L5 요소 종류 | 장소·단서처럼 **새 종류의 제작 요소와 그 칸·연결**을 정의 | 정하지 않음 |

**우려**: L5까지 가면 요소가 "고정 테이블의 행"이 아니라 "종류(스키마)를 가진 일반 객체"여야 한다. 그러면 지금의 테이블 구조(장소, 단서, 증언… 각각 별도 테이블과 복합 FK)는 맞지 않는다. 반대로 L2~L4만 목표라면 요소 종류는 고정으로 두고 규칙·모듈·화면 쪽만 열면 된다.

## 5. 편집기 구조의 원칙 (제안, 미확정)

1. **빈 곳에서 시작**한다. 정해진 입력 순서나 필수 단계가 없다.
2. **요소 중심**이다. 요소 종류별 목록 양식이 아니라, 요소를 만들고 그 요소의 **연결을 보고 편집**하는 것이 기본이다. 한 요소를 열면 "나를 가리키는 것 / 내가 가리키는 것"이 보인다.
3. **연결은 양방향으로 만든다**: 단서에서 장소를 고르거나, 장소에서 단서를 붙이거나. 고를 때 없으면 그 자리에서 새로 만든다.
4. **전체 구조를 한눈에 볼 수 있는 보기**가 있다(페이즈 흐름, 연결 지도 등). 형태(그래프 캔버스 / 목록 / 둘 다)는 미결정.
5. **연결이 없는 요소, 끊긴 참조**는 만드는 도중 막지 않고 표시만 한다. 확정 때 검사한다.
6. **규칙 편집은 편집기의 일부**다: 한 요소(장소, 단서, 페이즈…)에서 "이 요소에 일어나는 일(기믹)"을 바로 쓰고, 스크립트·한글 설명 보기·AI 프롬프트를 같은 자리에서 쓴다.
7. **시험하기가 있다**: 만든 것이 실제로 동작하는지 확정 전에 볼 수 있어야 한다.

## 6. 현재 구현·스키마와의 차이

- 화면: 테이블별 양식(`ContentPanel`)은 2·3·4·6번 원칙에 맞지 않는다. 연결을 보는 화면, 인라인 생성, 규칙 편집, 시험하기가 없다.
- 스키마: 연결이 고정 칼럼이라 "여러 장소에 걸친 단서", "기믹이 참조하는 요소의 목록", "작품별 설정값", "변수·태그"를 담을 곳이 없다. 기믹은 스크립트 본체와 달리 `조건`/`결과` 두 JSON 칼럼으로 되어 있다.
- 구조: 요소가 `(작품_번호, 순서)`로 식별되고 복합 FK가 걸려 있어 번호 재배열이 불가능하다(순서 변경 불가의 원인).
- 확정 스냅샷(`confirm.py`)의 형식(`형식버전` 1)은 현재 테이블 모양을 그대로 복사한 것이라 요소 모델이 바뀌면 같이 바뀐다.
- 재사용 가능성이 높은 것: 계정·작품·방·권한·라이브러리 버전 규칙·확정 흐름·실행 환경(Docker). 재검토 대상: 콘텐츠 테이블 구조와 작업공간 화면 전체.

## 7. 결정이 필요한 것

1. **새로운 기능의 범위**: 4.의 L1~L5 중 어디까지 제작자가 정의할 수 있어야 하는가. (L5를 포함하는지가 가장 큰 분기)
2. **연결의 일반성**: 연결을 고정 칼럼(테이블마다 정해진 참조)으로 둘 것인가, 모든 요소를 잇는 **일반 관계**(요소 A –[관계 이름]→ 요소 B, 제작자가 관계 종류도 정의)로 둘 것인가.
3. **편집 화면의 중심**: 요소 상세 편집+연결 목록 / 전체를 보는 그래프(캔버스) / 둘의 조합.
4. **기믹을 쓰는 자리**: 독립된 "기믹 라이브러리"에서 쓰고 붙이는가, 요소 옆에서 바로 쓰는가(또는 둘 다).
5. **시험하기의 형태**: 한글 설명 보기만 / 모의 실행(가짜 플레이어) / 혼자 시험 방 중 무엇부터.
6. **기존 콘텐츠 테이블의 처리**: 유지하고 위에 확장 층을 얹는가, 요소 모델을 새로 설계해 교체하는가. (1·2번 답에 따라 결정)
7. **시험할 작은 예시 작품**(질문 32, 미답): 설계가 실제 작품을 표현하는지 확인하기 위한 기준. 사용자가 만들고 싶은 기믹 예시(질문 12)도 함께 필요하다.

## 공간 구조와 게임 만들기 화면 (사용자 결정 2026-10-16)

- 로그인하면 **플레이공간**이 기본이다. 상단에서 **제작공간**·**기록공간**으로 이동한다(공간 이름은 가칭, `frontend/src/spaces.ts` 한 곳에서 바꾼다).
- **플레이공간** `/`: 입장코드로 방에 들어가기, 내가 방을 만들 수 있는 작품 목록(공개 작품 + 비공개 플레이 가능 작품, `GET /api/play-works`).
- **제작공간** `/make`: **게임 만들기**(`/make/games` → 작품 화면)와 **라이브러리 만들기**(`/make/library`: 진행단계·기믹) 두 갈래. 바로 게임 제작 화면으로 가지 않는다.
- **기록공간** `/records`: 게임 진행 기능이 없어 지금은 빈 화면이다.
- **게임 만들기 화면**: 동영상 편집처럼 가로로 진행되는 게임 흐름에 카드를 배치하고, 카드를 누르면 카드에서 세부 설정을 한다. **지금의 개요·장소/단서·사건·관계/자료·결말 탭은 모두 카드의 내용으로 옮긴다(사용자 결정).** 어떤 카드가 어떤 내용을 담는지는 미정이다(질문 중).
