# DB가 강제하는 규칙 vs 백엔드에서 구현·검증할 규칙

기준: `db/spec/schema_spec.xlsx`, 마이그레이션 `db/migrations/0001~0019`.
이 문서는 명세서의 자연어 제약조건이 어디에서 지켜지는지를 구분한다.
**"DB 강제"는 마이그레이션과 테스트로 확인된 것**이고, **"백엔드"는 DB만으로 구현할 수 없거나 구현하지 않기로 한 것**이다.

---

## 1. DB가 강제하는 무결성

### 1-1. 식별자와 키

| 규칙 | 구현 |
|---|---|
| 모든 테이블의 기본키는 `번호` INTEGER IDENTITY | `GENERATED ALWAYS AS IDENTITY` (32개 테이블). 번호를 직접 지정해 삽입하려면 `OVERRIDING SYSTEM VALUE`가 필요하다. |
| FK 컬럼의 타입은 참조 대상과 같다 | 모든 FK(62개) 컬럼이 INTEGER 이며 테스트가 전수 검사한다. |
| 작품 내부 번호는 작품 안에서만 유일하다 | `UNIQUE (작품_번호, 순서)` — 진행순서, 기믹적용, 인물, 장소, 단서, 증언, 조합, 사건, 엔딩분기, 후일담, 타임라인, 투표, 미디어 |
| 작품 내부 참조는 같은 작품 안의 순서만 가리킨다 | 복합 FK `(작품_번호, X_순서)` → 대상 `(작품_번호, 순서)` 22개. 다른 작품의 순서를 참조하면 거부된다. 순서 컬럼이 NULL 이면 검사하지 않는다(MATCH SIMPLE). |
| 버전은 작품별로 유일하다 | `UNIQUE (작품_번호, 버전)` — `진행`의 복합 FK 대상이기도 하다. |
| 라이브러리 항목(계열) = 계정+이름, 그 안에서 버전이 유일하다 | `UNIQUE NULLS NOT DISTINCT (계정_번호, 이름, 버전)` — `진행단계`, `기믹`. `계정_번호`가 NULL 인 공통 항목끼리도 중복되지 않는다(일반 UNIQUE 는 NULL 을 서로 다른 값으로 보기 때문에 `NULLS NOT DISTINCT` 가 필요하다). 같은 제작자가 같은 이름으로 만든 두 번째 행이 새 버전이다. 이름을 바꾸면 다른 계열이다 |

### 1-2. 값 범위 (CHECK)

| 테이블.컬럼 | 규칙 |
|---|---|
| 계정.상태 | `정상`, `정지`, `탈퇴` |
| 계정.권한 | `사용자`(기본값), `관리자`, `운영자` |
| 작품.공개권한 | `제작자`(기본값), `관리자`, `운영자` |
| 로그인세션.접속환경 | `PC`, `모바일` |
| 로그인세션.만료일시 | `> 생성일시` |
| 작품.최소인원 / 최대인원 | `최소인원 >= 1`, `최대인원 >= 최소인원` |
| 작품.상태 | `수정`, `개발`, `완료` |
| `순서` 컬럼 (14개 테이블 + 엔딩) | `순서 >= 1` |
| 진행순서.진행시간 | `>= 0` |
| 진행단계.버전 / 기믹.버전 | `>= 1` |
| 미디어.유형 | `이미지`, `영상` |
| 방.상태 | `대기`, `진행`, `종료` |
| 진행.상태 | `진행`, `종료` |

### 1-3. "정확히 하나만" 규칙 (확정: 정확히 1개)

| 테이블 | 규칙 |
|---|---|
| 조합재료 | `num_nonnulls(단서_순서, 증언_순서, 조합_순서) = 1` |
| 엔딩 | `num_nonnulls(엔딩분기_순서, 후일담_순서) = 1` |
| 획득 | `num_nonnulls(단서_순서, 증언_순서, 조합_순서) = 1` |

### 1-4. 복합 UNIQUE (게임 실행)

| 테이블 | 규칙 |
|---|---|
| 참여 | `(진행_번호, 계정_번호)` 한 판에 계정별 한 배역 / `(진행_번호, 인물_순서)` 한 배역에 한 계정 (인물_순서가 NULL 인 행은 여러 개 허용) |
| 기믹실행 | `(진행_번호, 기믹적용_순서)` ※ 해석 항목 — `SCHEMA_REPORT.md` 확인 요청 참조 |
| 투표결과 | `(작품_번호, 투표이름, 참여_번호)` 한 투표에 한 참여자가 한 번 (투표 이름은 진행단계 카드가 정한다. 0026) |
| 엔딩 | `(진행_번호, 순서)` |
| 진행구성 | `(작품_번호, 진행순서_순서, 진행단계_번호)` |
| 그 외 | 계정.아이디, 로그인세션.토큰 (방.입장코드는 종료되지 않은 방끼리만 유일, 0022) |

### 1-5. 제작용 콘텐츠 ↔ 게임 기록의 분리

- 게임 실행 테이블(`방`, `진행`, `참여`, `기믹실행`, `투표결과`, `엔딩`, `획득`)은 **제작용 콘텐츠 테이블(18개)과 라이브러리(`진행단계`, `기믹`)를 FK 로 참조하지 않는다.**
  `*_순서` 컬럼들은 `버전.시나리오` 스냅샷 안의 번호를 가리키는 일반 INTEGER 이다.
- 게임이 참조하는 것은 `작품`, `버전(작품_번호, 버전)`, `계정`, `방`뿐이다.
- 테스트(`test_isolation_and_triggers.py`)가 확인한 것: 제작용 콘텐츠를 전부 삭제하거나 수정해도 `방`~`획득`, `버전`의 모든 행이 변경 전과 동일하게 유지된다(행 내용 해시 비교).

### 1-6. 트리거 (`0006_triggers.sql`)

| 트리거 | 규칙 | 근거(명세서) |
|---|---|---|
| `tg_버전_불변` | `버전.시나리오`, `버전.작품_번호`, `버전.버전`은 INSERT 이후 변경 불가 (`변경사항`은 수정 가능) | 버전.시나리오 "확정 후 변경하지 않음" |
| `tg_진행단계_불변`, `tg_기믹_불변` | `삭제일시`(NULL → 값, 한 번만)와 `공개여부`(자유롭게 켜고 끔) 외의 UPDATE 는 모두 거부 (내용·이름·버전·소유자·변경내역 불변, 삭제 취소·삭제 시각 변경 불가). 수정은 버전을 올린 새 행으로 한다. 아무것도 바꾸지 않는 UPDATE 는 허용 | 사용자 결정(2026-10-14·15), `0011`·`0012` |
| `tg_방_시각` | 방.상태가 바뀌면 `상태변경일시` 갱신, `종료`가 되면 `종료일시` 기록 | 방.상태변경일시 / 종료일시 특징 |
| `tg_진행_시각` | 진행.상태가 `종료`가 되면 `종료일시` 기록 (이미 값이 있으면 유지) | 진행.종료일시 특징 |

### 1-7. 삭제 정책 (명세서에 없어 설계로 정한 부분)

| 대상 | 정책 | 이유 |
|---|---|---|
| 작품 삭제 → 제작용 콘텐츠, 버전 | CASCADE | 작성 중인 작품은 통째로 삭제 가능 |
| **게임이 있는 작품 / 확정 버전 삭제** | **거부 (RESTRICT)** | 게임·기록 보존. 아래 "한계" 참조 |
| 인물 삭제 → 관계 | CASCADE | 관계는 인물 없이 의미 없음 |
| 조합 삭제 → 조합재료(결과 쪽) | CASCADE | 레시피는 결과 조합 없이 의미 없음 |
| 사건 삭제 → 사건설명 | CASCADE | |
| 진행순서 삭제 → 진행구성 | CASCADE | 단계 배치는 순서 없이 의미 없음 |
| 다른 항목이 참조 중인 인물·장소·단서·증언·조합·진행순서 | 거부 (RESTRICT) | 단서→인물, 미디어→단서, 투표→진행순서 등. 선택적 연관을 조용히 NULL 로 바꾸면 의미가 변한다 (예: 인물별 후일담이 전체 후일담으로 바뀜) |
| 적용 중인 기믹, 진행구성이 쓰는 진행단계 | 거부 (RESTRICT) | 제작자의 "삭제"는 행을 지우는 것이 아니라 `삭제일시` 표시이다(아래 B39) |
| 계정 (작품·기록 보유) | 거부 (RESTRICT) | 탈퇴는 `상태='탈퇴'`로 처리해야 한다 |
| 계정 삭제 → 로그인세션 | CASCADE | |
| 작품·계정 삭제 → 테스터 | CASCADE | 테스터 지정은 보존할 기록이 아니다 |
| 진행 삭제 → 참여, 기믹실행, 엔딩, 획득, 투표결과 | CASCADE | 한 판의 기록은 판과 함께 |
| 방 (진행 보유) | 거부 (RESTRICT) | |

**한계:** 명세서에 작품의 "삭제됨" 상태가 없어서, 게임이 한 번이라도 진행된 작품은 DB에서 삭제할 수 없다. 사용자에게 삭제된 것처럼 보이게 하려면 별도의 방법이 필요하며, 이는 확인 요청 항목이다.

### 1-8. 인덱스

FK 컬럼마다 이를 앞쪽 컬럼으로 갖는 인덱스가 있다(테스트가 62개 FK 전수 검사). PK/UNIQUE 가 이미 덮는 경우를 제외하고 추가 인덱스 37개(`ix_*`)를 만들었다.

## 2. 백엔드에서 구현·검증할 규칙

> **명세서 위치**는 `시트.컬럼` 이다. "결정 필요"는 명세서나 대화에서 아직 확정되지 않은 항목이다.

### 2-1. 계정 / 세션

| # | 규칙 | 명세서 위치 | 비고 |
|---|---|---|---|
| B1 | 상태가 `정상`인 계정만 활성 (로그인 허용) | 계정.상태 | |
| B2 | 비밀번호 해시 저장, 토큰 해시 저장 (원문 저장 금지) | 계정.패스워드, 로그인세션.토큰 | 비밀번호는 느린 해시(Argon2id 등), 토큰은 추측 불가능한 무작위 값이므로 SHA-256 등 빠른 해시도 가능 |
| B3 | 세션 만료일시 계산: 자동로그인 해제 6시간, 설정 30일 | 로그인세션.만료일시 | 자동로그인 여부를 저장하는 컬럼은 없고 `만료일시 - 생성일시`로만 알 수 있다 |
| B4 | 로그아웃 시 폐기일시 기록, 폐기·만료된 세션은 인증 거부 | 로그인세션.폐기일시 | |
| B34 | 권한 3단계 `사용자` < `관리자` < `운영자`. 가입으로는 항상 `사용자`이며, 클라이언트가 보낸 권한 값은 무시한다. `관리자`는 운영자가 지정한다. 허용 범위(예정): 관리자는 문제 있는 방의 강제 폐쇄, 작품 비공개 처리 | 계정.권한 | **결정(사용자, 2026-10-14)**. 권한 변경·관리 기능은 아직 없다. 첫 운영자는 DB 에서 직접 지정한다(README). 권한 지정 기능은 나중에 관리자 페이지로, 방 강제 폐쇄 등 관리 기능과 운영자 고유 권한도 나중에(사용자 결정). 지금 권한이 의미를 갖는 곳은 B35·B36 뿐이다. 서버는 요청마다 DB 의 권한을 읽어 판단해야 한다 |

### 2-2. 작품 / 버전

| # | 규칙 | 명세서 위치 | 비고 |
|---|---|---|---|
| B5 | 최대인원 = NPC 가 아닌 인물 수로 자동 갱신 | 작품.최대인원 | **주의:** 기본값이 최소 4 / 최대 4 이고 `최대인원 >= 최소인원` CHECK 가 있다. 인물을 하나씩 추가하는 도중 계산값이 최소인원보다 작아지면 UPDATE 가 거부된다. 인물이 0명이면 최대인원 0 이 되어 `최소인원 >= 1`과 함께 만족할 값이 없다. 갱신 순서와 이 경우의 처리를 정해야 한다. |

> **결정(사용자, 2026-10-14)**: 인물(NPC 제외)이 0명이면 `최대인원`은 임시로 1 로 저장한다. 즉 `최대인원 = max(NPC 가 아닌 인물 수, 1)`.
> **구현**: `backend/app/characters.py` `sync_capacity()`. 작품은 최소·최대인원 1/1 로 시작하고 `최소인원`은 현재 `최대인원`을 넘길 수 없다(제약 `최대 >= 최소` 때문). 인물 추가는 인원이 늘기만 하므로 제약을 어기지 않는다. NPC 전환 등으로 인원이 `최소인원`보다 줄어드는 변경은 **미결정 상태에서 임시로 409 로 거부**한다 (사용자 확인 필요).

| B6 | 상태 전이 `개발` → `완료` → `수정` → `완료` 관리 | 작품.상태 | 허용 전이 정의 필요 |
| B7 | 개발·수정 중에는 `버전` 행을 만들지 않고, 완료 시 행 하나를 생성 | 버전 테이블 설명 | |
| B8 | 버전 생성 시 `작품.최신버전` 갱신, 작품.수정일시 갱신 | 작품.최신버전, 수정일시 | `버전.버전`은 TEXT 라서 대소 비교·증가 규칙(1.9 → 1.10)을 직접 정해야 한다 |
| B9 | 확정 시 스냅샷 생성: 제작용 콘텐츠 전체와, 사용된 기믹·진행단계 정의의 사본을 `시나리오`에 직렬화 | 버전.시나리오 | **구현됨(2026-10-15, `backend/app/confirm.py`)**: `POST /api/works/{id}/confirm`, 검사 `GET .../confirm/check`, 목록 `GET .../versions`. 버전은 `"N.0"`(앞자리 숫자 최댓값+1, 글자 순 비교 안 함). 오류(플레이어 인물 없음·페이즈 없음·최소인원>최대인원)는 확정을 막고, 경고(범인·엔딩·단서·타임라인 없음, 진행단계 없는 페이즈, 삭제된 라이브러리 연결)는 알리기만 한다. 스냅샷 `형식버전` 1: `작품`, `인물`, 콘텐츠 테이블 이름별 행 목록(`순서` 유지, `번호`·`작품_번호` 제외), `라이브러리`(진행단계·기믹 내용 사본, 삭제된 항목은 제외). 시각은 ISO 글자. 미디어는 아직 담지 않는다. `JSONB_COLUMNS.md` 참조 |

## 3. 사용 시 주의

- 모든 식별자는 큰따옴표로 감싸야 한다. 특히 `인물."NPC"` 는 대소문자 구분 이름이라 따옴표 없이 쓰면 `npc` 로 변환되어 찾지 못한다.
- `GENERATED ALWAYS` IDENTITY 이므로 `INSERT ... ("번호", ...)` 로 직접 번호를 넣으면 오류가 난다.
- 복합 FK 는 순서 컬럼이 NULL 이면 검사하지 않으므로, "선택적 연관"은 NULL 로 표현한다.
- 적용된 마이그레이션 파일은 수정하지 않는다 (체크섬 불일치로 실행기가 중단한다). 변경은 새 파일(`0007_*.sql`)로 추가한다.
