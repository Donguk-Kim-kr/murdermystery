# 백로그 (아직 만들지 않기로 한 기능)

사용자가 "나중에"로 미룬 항목과 그 이유·전제. 결정이 아니라 메모이다.

| 항목 | 내용 | 미루는 이유 / 전제 |
|---|---|---|
| 로그인 후 홈을 플레이 중심으로 개편 | 사용자가 많은 쪽은 제작자가 아니라 플레이어이므로, 로그인 후 첫 화면을 플레이 중심(공개 게임 목록, 방 입장)으로 바꾸고 제작은 별도 입구로 둔다. 참고: 쏘빅은 플레이룸(올라온 게임 목록)이 첫 화면이고 제작 툴은 별도 버튼으로 들어간다(사용자 제공 스크린샷). **방향만 정함, 상세는 나중에 다시 논의**(사용자) | 공개 작품 목록(아래 항목과 함께 보류됨), 게임 시작·플레이 화면이 필요하다. 플레이 화면은 PC·모바일 모두, 제작 화면은 PC 전용 |
| 세 공간 구조와 기록공간 (가칭, 2026-10-16 논의) | 큰 틀을 **플레이공간 / 제작공간 / 기록공간** 셋으로 나눈다(공간 이름은 가칭). ① 플레이공간: 홈이 곧 작품 목록이고 카드를 누르면 작품 상세(쏘빅식)가 열리며, **게임을 고른 뒤 거기서 방을 연다**(방 1개 = 게임 1개). 별도의 "게임 고르기" 버튼이나 로비는 두지 않는다. 공개방은 없으므로 **입장코드 입력 입구**(상단 입력칸 하나)와 "내 방" 표시(한 계정은 한 번에 한 방)가 필요하다. ② 기록공간: 내가 플레이한 판의 기록. 작품 이름, 캐릭터 이름, 엔딩, 평점, 난이도, 후기, 내 메모, 플레이 날짜. 범인 검거 여부는 "성공" 표시 대신 내 투표·실제 범인·도달한 엔딩 같은 **사실을 나열**한다(투표 규칙이 정해지기 전이라 성공 기준이 없다). 개인 목표 성공 여부·점수·획득한 단서(소유 이력이 안 남음)는 고민 중. ③ 데이터: `참여`에 평점·난이도·후기공개·메모를 추가했다(B33, `0016`). | 게임 시작·진행 기능이 없어 기록이 쌓이지 않는다. **정해진 것(2026-10-16)**: 엔딩 이름은 `엔딩분기.이름`(`0017`) / 같은 작품 반복 플레이는 별도 처리 없이 판마다 센다 / 기록의 작품 제목은 지금의 제목 / 비공개 후기는 제작자에게 "비공개" 표시만 붙여 그대로 보여 준다(작성자 표시는 다른 후기와 같은 방식으로 가정, 필요하면 다시 확인). **아직**: 개인 목표 성공 여부·점수·획득한 단서 표시 |
| 위시리스트·플레이리스트 (같은 기능) | 사용자별로 작품을 담아 두는 목록 | 담을 작품을 보여 주는 **공개 작품 목록이 보류**(사용자 결정)라서 화면이 없다. 새 테이블이 필요하다(예: 계정·작품·종류·추가일시, UNIQUE(계정, 작품, 종류)) |
| 플레이한 게임 숨기기 | 플레이 기록이 있는 작품은 작품 목록에서 안 보이게 | 위와 같은 이유 + **플레이 기록**(방·참여 기능)이 아직 없다. 기록은 `참여`→`진행`→작품으로 조회할 수 있어 새 컬럼은 필요 없을 가능성이 높다(`진행`에는 계정이 없어 `참여`를 거쳐야 하고, 대기실만 다녀간 입장자는 DB에 기록되지 않는다). 사용자가 다시 보고 싶을 수 있으므로 켜고 끄는 선택이 필요해 보인다(미확정) |
| 관리자 화면 | 권한 지정, 방 강제 폐쇄, 작품 비공개 처리 | 관리자 페이지를 따로 만들 예정(사용자 결정). 비공개 처리 API 는 이미 있다(`publishing.py`) |
| 확정 전 검증 툴 | 논리·스토리 검증 후에만 확정·공개 | 검증 방식 미확정(사용자 결정). 공개 조건(B10)은 이 기능과 함께 `ensure_can_publish()` 에 넣는다 |
| 라이브러리 항목 화면·API | `진행단계`·`기믹`을 만들기·버전 올리기·삭제하기·고르기(고를 때 버전과 변경내역 표시, 삭제된 항목은 '삭제된 항목'으로 표시), 새 버전이 나왔을 때 작품에 알리기, 운영자에게만 "공통 항목으로 만들기" 선택 버튼 보여 주기, 삭제된 버전을 쓰던 작품에도 새 버전을 안내할지 정하기 | 제작 화면과 관리자 페이지가 아직 없다. 규칙은 DB_RULES B39 |
| 만들다 만 작품·기믹·진행단계 정리 | 사용자가 중간에 그만두는 항목이 많을 것이라 정리 방법이 필요하다(사용자: "나중 문제"). 삭제된 항목도 이름·버전을 점유하므로 한 번도 쓰이지 않은 항목은 실제로 지우는 방안 등을 그때 정한다 | 사용 패턴을 본 뒤 결정 |
| 라이브러리 삭제 취소 | 삭제 표시를 되돌리는 기능 | 지금은 트리거가 막는다. 필요해지면 트리거를 완화한다 |
| 라이브러리(기믹·진행단계) 공유 | 다른 제작자의 공개된 항목을 선택해 쓰기. 컬럼(`공개여부`)은 이미 있다 | 필요한 것: 선택 목록에 공개 항목 추가, 기믹이 작품별 값을 인자로 받는 구조(`기믹적용` 설정 컬럼), 공개 전 검수·신고·출처와 이용 조건 표시, 한글·영어 이름이 섞일 때의 영문 별칭. 삭제는 표시 방식이라 쓰던 작품이 깨지지 않는다 |
| 운영자 고유 권한 | 운영자만 할 수 있는 일 | 사용자가 나중에 정하기로 함 |
| 제작자 글꼴 (작품·플레이 화면용) | 사이트가 검수해 등록한 **공용 글꼴 카탈로그**에서 제작자가 작품 테마의 글꼴을 고르고, 즐겨찾기로 자주 쓰는 글꼴을 먼저 보여 줌 | 방향은 결정(2026-10-14), 설계는 미착수. 아래 "글꼴 메모" 참고. 작품 테마 설정 형식은 JSONB 형식 논의와 함께 정한다 |

## 글꼴 메모 (2026-10-14 대화)

### 결정
- **지금은 운영자(사용자)가 제공하는 글꼴만 쓸 수 있다.** 글꼴은 지금 프로젝트에서 우선순위가 낮다.
- **구조는 두 출처를 모두 지원하도록 설계**하고, **제작자 업로드는 서버에서 막아 둔다.** 프론트엔드에서 버튼을 숨기는 것만으로는 막히지 않는다(API 를 직접 호출할 수 있다). 업로드 API 를 만들 때 서버 설정(예: `MM_FONT_UPLOAD_ENABLED=false`, 기본 꺼짐)으로 거부해야 한다. 업로드 API 는 아직 없다.
- 라이선스로 글꼴을 내릴 때: 항목은 지우지 않고 **사용 중단**으로 바꿔 새 선택을 막고, 이미 확정된 작품에서는 기본 글꼴(Pretendard)로 대체해 보여 준다. 운영자만 되돌릴 수 있다(B35 와 같은 구조).
- 등록 기준: 상업 사용 · 웹 임베딩 · 파일 재배포가 모두 허용되는 글꼴(OFL 등). 검수 자동화는 나중에(후보: 패키지 메타데이터에 라이선스가 표기된 출처만 반자동으로).
- 글꼴 카탈로그는 즐겨찾기(위시리스트와 함께 설계)와 별개로 두며, 계정별 보관함은 두지 않는다.

### 설계안 (미확정 — 테이블은 아직 만들지 않았다)
단일 테이블 `글꼴` 하나로 두 출처를 모두 담는다.

| 컬럼 | 설명 |
|---|---|
| 번호, 이름 | 이름은 화면에서 부를 font-family 이름 |
| 경로, 파일해시 | 파일 위치와 SHA-256. 확정된 작품이 쓰는 파일이 바뀌지 않았는지 확인하고(B20) 중복을 막는다 |
| 출처 | `운영자` / `제작자`. 운영자 글꼴은 모든 작품에서, 제작자 글꼴은 **등록한 계정의 작품에서만** 쓸 수 있다(백엔드 검증) |
| 등록자_번호 | 올린 계정. 운영자 글꼴은 운영자 계정 |
| 상태 | `검수대기` / `사용가능` / `사용중단` / `반려`. 운영자 글꼴은 바로 `사용가능`, 제작자 글꼴은 검수 후 `사용가능` |
| 라이선스, 출처URL, 검수자_번호, 검수일시 | 검수 기록 |

- 굵기·기울임 지원 여부는 미정(처음에는 글꼴당 파일 하나, 가변 글꼴 가능).
- 작품 테마가 어떤 글꼴을 쓰는지는 테마 설정 형식(JSONB 형식 논의)에서 정하며, 확정 스냅샷에는 글꼴의 번호·이름·파일해시와 대체 글꼴을 기록한다.
- **이 테이블은 글꼴을 쓰는 곳(작품 테마)이 생길 때 함께 만드는 것을 권한다.** 쓰는 곳 없이 먼저 만들면 사용 방식이 정해질 때 다시 고칠 가능성이 크다.

### 미정
- 제작자가 개인적으로 구매한 글꼴을 쓰게 할지. `@font-face` 로 적용한다는 것은 다른 참여자의 브라우저가 서버에서 글꼴 파일을 받는다는 뜻이라 웹 임베딩 허용 여부가 걸린다. 사이트가 소유 여부를 검증할 수 없다. (서버가 파일을 보내지 않는 `local()` 방식은 설치한 사람에게만 보인다.)
- 한글 글꼴은 글자 범위별로 쪼개 필요한 조각만 받는다(앱 글꼴 Pretendard: 92조각 중 로그인 화면 6조각, 153KB).
- 앱 글꼴 Pretendard `ss05`(부호를 한글 높이에 맞춤)는 전체에 적용했다.

## AI 기능 메모 (2026-10-14 대화, 구현 아님 — 가능성 검토)

사용자 구상: 1차 **AI 시나리오 검증** → 2차 **AI 테스트플레이**(AI 여러 명이 플레이) → 3차 **AI 등장인물**(NPC 또는 빈자리를 채우는 대역). GPT 와의 대화를 가져와 가능성을 검토했다.

### 방향 (사용자 의견)
- **알리바이·시간 충돌은 `타임라인`으로 푼다.** 데이터는 제작자가 직접 만들어 책임진다. AI 가 초안을 만들더라도 제작자가 확인·확정한다.
- 규칙 기반 검증(시간표 충돌 등)은 AI 가 아니라 일반 코드로 한다. 비용이 거의 들지 않고 결과가 항상 같다.
- **타임라인을 입력하지 않은 작품도 허용**할 수 있다는 의견(더 생각해 보기로 함). 이 경우 시간 관련 검증은 "검증하지 않음"으로 표시하고, 비어 있는 것을 "문제 없음"으로 보여 주면 안 된다.

### `타임라인` 구조 (미정, 더 고민하기로 함)
- 현재 `타임라인`은 "사건의 진상 타임라인": 시작시간·종료시간·설명(TEXT)뿐이다. **텍스트로 둔 이유(사용자)**: 제작자가 여러 인물을 함께, 또는 인물이 없는 상황도 자유롭게 적을 수 있게 하려는 것.
- 후보: 특정 인물의 행동을 묘사하기 위해 `인물_순서`를 NULL 허용으로 추가. 알리바이 검사에는 이것만으로 부족하고 장소(`장소_순서`), 사실/진술 구분, 장소 간 이동 시간이 더 필요하다. 한 행에 여러 인물이 섞인 텍스트는 코드가 검사할 수 없으므로, 검사는 인물·장소·시간이 모두 채워진 행에만 적용된다. 텍스트 서술은 그대로 두고 구조화 행을 선택으로 더하는 방식이 후보.
- 명세서 변경이라 결정 전에는 만들지 않는다. 엔진 설계(JSONB 계약) 논의와 함께 정한다.

### 확정 전 검증과의 관계 (제안, 미확정)
- AI 검증은 확정·공개의 **필수 조건이 아니라 경고용 보조**로 두는 안: 오탐이 제작자를 막으면 안 되고 호출 비용이 든다. (사용자 미결정)

### 비용·운영 (미정)
- 무료 사이트를 지향하는 이유: 운영자가 아직 유료로 운영할 준비(사업자 등록 등)가 안 되어 있다.
- AI 호출 비용이 실제로 크면 후보: ① 제작자 본인의 API 키 연결 ② 사용 횟수당 비용을 받는 방식. 어느 쪽이든 미정. ①은 결제 처리가 필요 없지만 제작자의 키를 안전하게 보관해야 한다.
- GPT 비용 문서의 숫자(토큰 단가, 호출당 토큰 수)는 가정이라 믿지 않는다. 5인용 시나리오 한 편으로 실제 호출량을 측정한 뒤 판단한다.
- 제작자의 미공개 시나리오(범인·비밀 포함)가 외부 AI 서비스로 전송되므로 사용 고지와 동의가 필요하다.

### 순서에 대한 판단 (사용자 미결정)
- 사람 플레이 엔진 → LLM 시나리오 검토(가장 쉬움) → AI NPC → AI 테스트플레이·대역 순. AI 테스트플레이는 사람 플레이 엔진의 행동 API 위에서 동작하므로 엔진이 먼저 필요하다.
- 음성은 Discord 로 하므로 AI 대역이 대화에 참여하려면 사이트 안 채팅이나 Discord 봇이 필요하다(현재 없음).

## 로그인·패스워드 (2026-10-18 결정, 모두 구현됨)

- **로그인 실패 메시지**: 아이디가 없으면 "아이디가 존재하지 않습니다", 패스워드가 틀리면 "패스워드가 올바르지 않습니다 (남은 시도 N회)". 계정 존재가 알려지는 점은 감수했다(가입 화면이 이미 "이미 사용 중인 아이디입니다"로 알려 주고 있었다). 없는 아이디의 시도는 세지 않는다.
- **패스워드 입력 제한**: 같은 아이디로 연속 10회 틀리면 5분 동안 로그인을 막고(맞는 패스워드도 받지 않음, 응답 429), 5분 뒤에 처음부터 다시 센다. 성공하면 0으로 돌아간다. 아이디 기준만이고 접속 IP 기준은 두지 않았다. 서버 메모리에 두므로 서버를 다시 시작하면 풀린다(`backend/app/auth.py` `LoginGuard`, 설정 `MM_LOGIN_FAIL_LIMIT`·`MM_LOGIN_LOCK_SECONDS`).
- **패스워드 초기화**: 로그인 화면의 "패스워드를 잊으셨나요?". 아이디와 닉네임이 둘 다 맞으면 새 패스워드를 정한다(`POST /api/auth/reset-password`). 닉네임은 같이 플레이한 사람에게 보이므로 약한 확인이라는 점은 알고 받아들였다. 실패는 로그인 실패와 합쳐 세어 같은 제한을 받고, 바꾸면 그 계정의 로그인 세션을 모두 끊는다. "패스워드가 바뀌었습니다" 알림은 따로 보여 주지 않는다. 더 강한 방법 후보(필요해지면): 이메일 인증, Discord 연동, 가입 때 일회용 복구 코드, 운영자 수동 초기화. 휴대폰 본인인증은 업체 계약과 사업자 등록이 필요해 쓸 수 없다.
- **가입 화면**: 안 되는 입력이 있으면 어느 항목이 왜 문제인지 알려 준다. 로그인·회원가입·패스워드 찾기 화면을 오가면 입력한 내용이 비워진다.
- **패스워드 규칙**: 가입·초기화할 때 **8자 이상 128자 이하**(문자 종류 조건 없음). 시험할 때는 환경변수 `MM_PASSWORD_MIN_LENGTH` 로 최소 글자 수를 낮출 수 있다(`docker-compose.yml` 에 임시로 1 을 넣어 두었으니 시험이 끝나면 그 줄을 지운다).

## 단서·증언·조합의 이름 2개 — 구현 완료 (2026-10-18, 사용자 결정)

- **공개이름**: 남들에게 보이는 이름(예: "A의 서랍", "지나가던 사람"). **이름**: 진짜 이름(예: "커터칼", "A의 마약소문"). 단서·증언·조합 모두 같다. DB 컬럼 이름은 `공개이름`(비워 둘 수 있다, 0023), 제작 화면에는 입력칸이 하나 더 있다.
- 증언은 `화자` 를 `공개이름` 으로 바꾸고 진짜 이름 `이름`(필수)을 더했다. 이미 있던 증언의 이름은 "<화자>의 증언" 으로 채웠다.
- 보이는 곳: 내 단서 탭과 공개된 단서 탭의 카드는 **공개이름 → 그 아래 진짜 이름** 이 보이고, 누르면 내용이 펼쳐진다(내용이 길 수 있어서). 보여 주기·양도·전체 공개도 같은 카드 모양이다. 공개이름을 비워 두면 이름 하나만 보인다.
- **조사 결과 블록은 없앴다.** 조사하면 얻은 것이 내 단서 탭으로 들어올 뿐이다(기본 조사 진행단계 v3).
- 스크립트: `가지고_있다`·`단서_보유자` 는 **진짜 이름**(`이름`)으로 찾는다. `보유목록`·`카드목록`·`조사`·`모든_단서` 가 주는 카드에는 `이름` 과 `공개이름` 이 모두 들어 있다.
- 조사 화면의 장소 선택에는 단서 이름이 나오지 않는다(장소만 고른다). 장소를 고르기 전에 공개이름을 보여 주는 화면은 아직 없다.

## 조합 입력 화면 합치기 — 구현 완료 (2026-10-18)

- 조합을 만드는 화면 하나에 이름·공개이름·내용·기능과 **재료**가 함께 있다. 재료는 **단서 / 증언 / 조합 넣기** 버튼을 누르면 그 종류의 목록이 나오고, 하나를 고르면 추가된다(빼기 가능). "조합 재료" 목록은 화면에서 숨겼다(API·스냅샷에는 그대로 있다).
- 저장은 한 요청(`재료: [{종류, 순서}]`)이고, DB 에는 `조합`·`조합재료` 로 나뉘어 저장된다. 고칠 때 재료를 보내면 통째로 바뀌고 보내지 않으면 그대로이다.
- 같은 재료를 여러 번 넣어도 한 번만 저장되고 화면에도 하나만 보인다(이미 넣은 재료는 목록에서 빠진다). 조합이 자기 자신이나 서로를 재료로 쓰는 순환은 저장할 때 거부한다(만들 때는 생길 수 없지만 고칠 때 생길 수 있어서 검사를 남겼다).
- 확정할 때 재료가 없는 조합이 있으면 경고한다.

## 제작 화면에서 식과 JSON 을 없애기 (사용자 설계 2026-10-18, 아직 구현 전)

- **원칙**: 식(조건식·스크립트)은 **진행단계와 기믹을 만드는 쪽에만** 있다. 제작자는 식을 쓰지 않는다. 지금 구현과 어긋나는 곳이 아래 두 가지이다.
  1. **흐름의 카드 설정**: 입력칸·선택지로만 설정한다(예: 조사 횟수). 지금은 `동률`·`재투표후보`·`재투표한도` 등이 "그 밖의 세부 설정(JSON)" 칸에 있다. 조사는 **모두 1개씩 n번**이 기본이다(이미 그렇게 동작).
  2. **엔딩 분기·후일담의 조건**: 지금은 결말 탭에서 `{"식": …}` 을 직접 쓴다. 제작자가 **목록에서 고르는 방식**으로 바꿔야 한다. 기본 조건(투표 결과, 개인 질문 답변, 능력 사용·지목 대상)은 제작자가 고르고, 그보다 복잡한 조건은 제작자가 기믹·진행단계로 만든다.
- **조건 고르기가 성립하려면**: 고를 항목을 화면이 알아야 한다. 투표 결과(범인 검거·동률·투표 없음·특정 인물·기타 선택지)와 개인 질문 답변은 흐름에 놓인 카드에서 알 수 있다. 능력 사용 결과와 기믹이 남기는 값은 **그 진행단계·기믹이 "내가 남기는 값(이름·종류·고를 수 있는 값)"을 미리 적어 두어야** 목록에 나온다. 이 선언 방식과 능력의 사용 방식(단계 7)은 정해지지 않았다.
- 내부 저장은 지금처럼 식으로 만들어 두어도 되지만, 화면에서는 보이지 않아야 한다.
- **구현된 것(2026-10-18)**: 흐름 카드 설정 중 `횟수`·`보여주기허용`·`양도허용`·`동률`·`재투표후보`·`재투표한도`·`대상`·`안내` 는 입력칸·선택지로 정한다(스크립트가 읽는 것만 보인다). 능력은 기본 진행단계 "능력 사용" 으로 지목하며 대상은 인물·장소·단서(사용자 결정). 전체 시나리오 중 원할 때 쓰는 능력은 기믹으로(단계 7).
- **구현된 것(2026-10-18, 이어서)**: 진행단계 스크립트가 `설정정의`·`조건정의` 두 함수로 흐름 카드의 입력칸과 엔딩·후일담 조건 항목을 스스로 정한다(`ENGINE_SPEC.md` 10). 결말 탭은 식 대신 이 항목을 고른다. 프런트에 박아 둔 설정 목록은 없앴다.
- **남은 것**: 기믹이 남기는 값도 같은 방식으로 선언하기(단계 7), "그 밖의 세부 설정(JSON)" 칸과 라이브러리 `규칙` JSON 칸을 제작자에게서 숨기기, 카드 이름을 다르게 정한 같은 종류의 카드를 여러 번 놓은 경우 투표 카드의 조건(투표 이름이 고정이라 구분되지 않음).

## 기본 진행단계 정리 (사용자와 한 장씩 토론, 2026-10-18~)

진행 방식: 한 장씩 설정을 대화로 토론하고, 확인하고, 고친다. 정한 것은 아래에 남긴다.

- **1. 공통 스토리(옛 프롤로그)** — 결정: 전원 확인 전에도 넘어갈 수 있다(현재 유지). 확인 버튼은 "다 읽었는지 묻고 확인하고 넘어가는 과정"을 버튼으로 한 편의 기능이라 유지한다. 이름은 "공통 스토리". 공통 스토리를 개인 서사처럼 부분(최대 5)으로 나누고 카드가 보여 줄 부분을 고른다. 모든 탭은 이름을 바꿀 수 있고, 공통 스토리·개인 서사는 "새 탭 추가(기본) / 기존 탭에 이어서"를 고른다(구현 완료, `ENGINE_SPEC.md`).
- 이름 붙이기: 같은 진행단계를 여러 번 놓으면 카드 이름은 "1차 ○○", "2차 ○○"로 자동으로 붙는다. 카드마다 임의의 이름은 정할 수 없다(페이즈 이름과 탭 이름은 직접 정할 수 있다).
- **2. 캐릭터 선택** — 결정: 각자 고르는 방식만(무작위·방장 지정 없음). 확인 뒤에도 다음 단계로 넘어가기 전에는 취소 가능(정정). 전원이 고르기 전에는 못 넘어간다(유지). 관전자는 현황만. **NPC 규칙**: 인물은 항상 NPC / NPC가 될 수 있는 인물(순위) / 반드시 플레이하는 인물 세 종류이고, 최대·최소 인원은 인물에서 자동 계산한다. 인원이 최대보다 적으면 제작자가 정한 순위대로 인물이 NPC 가 되어 선택 목록에서 빠진다. 인물의 소개는 둘로 나누었다: 캐릭터 설명(`캐릭터설명`, 카드 설정 `설명보이기`로 보임, 기본 끔)와 자기소개 멘트(`소개`). (구현 완료, `ENGINE_SPEC.md`.) 지난번 제가 "인원보다 인물이 많으면 남는 인물은 무배정"이라고 한 설명은 틀렸다. 이미 시작 조건이 인원 = 인물 수였다.
- **3. 프로필 숙지** — 결정: 서사뿐 아니라 **타임라인·비밀·목표·능력(무엇인지만)** 도 개인 서사 탭에 나온다(모양은 탭 하나에 구역으로). 직업·나이·성별은 캐릭터 선택 이후 언제든 볼 수 있는 **"캐릭터 설명" 탭**에 둔다(캐릭터 선택 카드가 만듦). 카드마다 보여 줄 항목을 고를 수 있고(1차에는 서사, 2차에는 비밀 공개 같은 쓰임), **따로 고르지 않으면 항목도 서사 부분도 전체가 보인다**(공통 스토리의 기본 1부분과 다르다). (구현 완료, `ENGINE_SPEC.md`.) 캐릭터 설명 탭은 **다음 단계로 넘어갈 때 만들어진다**(사용자 정정 2026-10-18, 선택하는 동안에는 없다. 선택 화면에서 직업·나이·성별이 보이는 것은 맞다). 이를 위해 스크립트에 페이즈를 떠날 때 실행되는 `종료(카드)` 함수를 더했다.
- **4. 자기소개** — 결정: 탭에는 **소개 멘트만** 둔다(직업 등은 캐릭터 설명 탭). 소개 멘트가 있는 인물은 한꺼번에, 등장인물 순서대로 보여도 된다. 한 사람씩 하는 순서·차례 표시는 필요 없다. 탭은 기본으로 남기고, 사라지게 하는 것은 기존 `내용 유지` 설정으로 정한다(처음에는 기본을 사라지게 하라고 하셨다가 정정). 멘트 앞에 인물 이름 한 줄을 붙였다(누구의 멘트인지 알 수 있게. 사용자 확인: 지금은 그대로 둔다. 제작자는 보통 대사 왼쪽에 캐릭터 이미지를 넣으므로 이미지 업로드·표시를 만들 때(단계 7) 이름 줄을 이미지로 바꾸는 것을 함께 본다). (구현 완료, `ENGINE_SPEC.md`.)
- **5. 조사** — 결정(정정): 장소를 고르면 항목이 나오는 것이 아니라 **장소의 단서·증언 중 하나를 직접 고른다**(목록에는 공개이름). 단서는 선착순 한 명이라 가져간 단서는 회색, 증언은 각자 얻을 수 있다. 1인당 N번이고 얻지 못할 때는 횟수를 쓰지 않는다. 다른 사람이 무엇을 조사했는지는 **보이게 하는 게임과 아닌 게임이 모두 있어** 카드 설정 `조사공개`로 둔다(**기본 켬**, 사용자 정정). 획득한 순간 "'공개이름'을 획득했습니다. 단서 탭에서 확인하세요" 알림을 띄우고(조사는 받침에 맞게 자동), 획득하지 못했을 때의 실패 알림은 없다(회색으로 이미 보인다). 누가 가졌는지 표시는 닉네임이 아니라 **캐릭터 이름**이고, 조사공개를 끄면 표시 없이 고를 수 없는 항목(회색)이 될 뿐이다. 화면·설정·문서의 표현은 "획득"으로 통일한다. 횟수를 다 쓰면 더 조사하지 못한다. 단서 먼저·증언 나중 같은 우선순위는 없다. (구현 완료, `ENGINE_SPEC.md`.) 장소별 목록은 카드 형태이고 지도형은 단계 7이다.
- **6. 토론** — 결정: 카드·페이즈 이름은 그대로(토론, 밀담은 말로 하는 단계). 단서는 **보여주기**(한 명·여러 명·전체, 취소하면 상대 화면에서 사라짐)와 **양도**(수락 없이 바로 받는 사람의 "내 단서"가 됨)만 한다. 증언은 보여주기·양도 없음. 받은 공개는 **"공개 단서" 탭**(이름 변경 가능)에 쌓이고 카드에 "○○가 단서를 공유했습니다"(○○는 보여 준 사람의 캐릭터 이름, 닉네임은 쓰지 않음)로 표시한다. 양도하는 사람에게는 알림이 없고, 받는 사람에게는 "○○님이 단서를 양도했습니다."(○○는 양도한 사람의 캐릭터 이름, 없으면 닉네임)가 뜬다. 최초 습득자·양도 경로는 보이지 않는다. 대상은 NPC를 제외한 플레이어. 토론 시간 표시는 사용자가 UI를 정할 때 결정한다. (구현 완료)
- **7. 밀담** — 결정: 밀담은 다른 단계와 함께 가는 페이즈라 페이즈 이름(예: 토론·밀담)에 밀담이 붙는 것으로 충분하다. 카드는 **"밀담 가능" 표시만** 보여 주고 안내 문구 설정은 없앤다(안내는 함께 가는 단계에서 정함). (구현 완료)
- **8. 추리 발표** — 결정: 밀담과 같다. 발표는 Discord 에서 하고, 카드는 **"추리 발표 중" 표시만** 보여 준다. 안내 문구 설정은 없애고(안내는 함께 가는 단계에서), 시간은 페이즈의 진행 시간으로 정한다. (구현 완료)
- **9. 최종 투표** — 결정(1차): 엔딩·후일담 조건은 **"범인을 검거했다" / "범인을 검거하지 못했다(검거 실패)" 둘뿐**이다. 동률·투표 없음·특정 인물·인물이 아닌 후보 조건은 없앴고, 동률이나 투표 없음, 인물이 아닌 후보가 1위인 결과는 모두 검거하지 못한 것으로 본다. (구현 완료; 후보·동률 처리·재투표 설정과 화면 문구는 이어서 정한다)
- 다음: 9. 최종 투표의 나머지(후보·동률 처리·재투표)부터 이어서 한다(10~14는 위 표 참고).
