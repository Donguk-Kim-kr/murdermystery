# 게임 엔진 설계 메모 (2026-10-15 대화)

JSONB 형식(조건·규칙·결과)과 게임 진행 방식을 정하기 위한 대화의 기록이다.
**명세가 아니라 메모**이며, 구현은 아직 없다. 사용자가 정한 것과 제안(미확정)을 구분해 적는다.

## 1. 사용자가 정한 것

### 1-1. 게임 흐름
- 한 판은 `진행순서`(페이즈) 여러 개가 순서대로 이어진다. 페이즈마다 진행시간(분)이 있다. 라운드 구분은 두지 않는다.
- 한 페이즈에는 `진행구성`으로 진행단계를 여러 개 연결할 수 있다(예: 토론+밀담+조사를 동시에).
- 공통 진행단계(운영자가 `계정_번호` NULL 로 등록할 예정): 프롤로그, 캐릭터 선택, 프로필 숙지, 자기소개, 조사, 토론, 밀담, 추리발표(개인), 투표, 에필로그, 후일담.
- **기본 진행단계 정리(사용자, 2026-10-17, 위 목록을 대체)**: 단계별로 플레이어가 조작할 내용은 사용자가 이어서 알려 주기로 했다.

  | 진행단계 | 역할 |
  |---|---|
  | 프롤로그 | 공통 스토리 공개 |
  | 캐릭터 선택 | 플레이어별 캐릭터 선택 |
  | 프로필 숙지 | 본인의 개인 서사 열람 |
  | 자기소개 | 각자 자기소개 진행 |
  | 조사 | 장소·소지품 등을 조사해 단서 획득 |
  | 토론 | 전체 플레이어의 토론 |
  | 밀담 | 일부 플레이어의 대화. 별도 추가 기능 없이 유지(밀담 가능 여부를 안내만 한다. 토론과 같이 가는 경우가 많다) |
  | 추리 발표 | 각자의 추리 발표 |
  | 최종 투표 | 각자 가장 범인일 것 같은 사람을 투표하고 최다 득표자가 구속된다. **자기 자신에게는 투표할 수 없다** | **동률 규칙**(제작자가 고른다): 동률을 **재투표**로 풀거나 구속 없음으로 한다. 재투표를 고르면 ① 재투표 후보(동률인 사람만 / 전체) ② 재투표 횟수 한도(**한도 없음도 지원**, 한도 없음이면 **시간이 끝나도 동률이 풀릴 때까지 반복**) ③ 한도까지 동률일 때의 처리(**구속 없음**. 무작위는 없다, 사용자 결정 2026-10-17)를 정한다. **우선권은 기본 틀에서 뺀다(사용자 결정 2026-10-17)**: 필요한 제작자가 기믹으로 만든다(그러려면 기믹이 투표 결과·동률을 받아 구속 대상을 정할 수 있어야 한다) |
  | 엔딩 | 최종 투표 결과에 따른 이야기 공개 |
  | 후일담 | 사건 이후 이야기 공개. 캐릭터별 후일담도 보통 모두에게 공개 |
  | 전체 공개 | 게임 종료 후 모든 단서와 작품 내용 열람 |

  - **에필로그는 `엔딩`으로 이름을 바꾼다**(사용자, 2026-10-17). 위의 이전 목록과 마이그레이션 `0015` 의 시험용 기본값에는 옛 이름이 남아 있다(진행단계 이름은 제작자가 라이브러리에서 정하는 값이다).
  - 이전 목록과 달라진 점: `추리발표(개인)` → `추리 발표`, `투표` → `최종 투표`(구속 대상 결정이 추가), `전체 공개`가 새로 있음(진행단계로 둘지는 확인 필요).

- **기본 진행단계별 동작과 제작자가 고르는 설정(사용자, 2026-10-17)**: 설정 항목은 카드를 놓는 자리의 `진행구성.설정`에 담을 후보이다(내부 구조 미정).

  | 진행단계 | 동작 | 제작자가 고르는 설정 |
  |---|---|---|
  | 프롤로그 | 모든 플레이어에게 공통 스토리를 보여 준다(보통 전체 공개) | 없음(공통 스토리는 따로 수정할 내용이 없다) |
  | 캐릭터 선택 | 각자 등장인물 중 하나를 **선착순**으로 고른다(정해진 인물 중에서) | 없음 |
  | 프로필 숙지 | 각자 자기 인물의 개인 서사를 본다(자기 서사만) | **카드마다 각 캐릭터에게 보여 줄 개인 서사를 고른다**(→ 1-4-6) |
  | 자기소개 | 각자 자기소개를 한다. 제작자가 준 소개 멘트가 있으면 보여 주고, 없으면 플레이어가 알아서 한다. 멘트는 보통 공용 정보로 모두가 볼 수 있다 | 소개 멘트는 `인물`의 새 컬럼 `소개`에 둔다(추가 예정, 아직 없음) |
  | 조사 | 각자 단서를 얻는다. **장소를 고른다**(게임마다 방법이 다르다). 상대의 소지품을 마음대로 확인하는 것은 안 된다 | 선착순으로 몇 개인지 / 동시에 1개씩이면 총 몇 번인지, 화면에 보여 줄 문구 |
  | 토론 | 전체가 대화로 토론한다. 얻은 단서를 **보여 주기·양도**할 수 있다(교환은 없다: 서로 양도하면 교환과 같다). 상대의 단서는 상대가 보여 주거나 양도할 때만 볼 수 있다 | 보여 주기·양도의 허용 여부 |
  | 밀담 | 일부 플레이어만 대화한다. 사이트는 안내 문구만 보여 주고 진행은 Discord 에서 한다 | 안내 문구(제작자가 쓴다) |
  | 추리 발표 | 각자 자기 추리를 발표한다 | 진행 시간(플레이어 수에 따라 제작자가 조절. 기본은 플레이어당 1분 안팎) |
  | 최종 투표 | 각자 가장 범인일 것 같은 사람을 투표하고 최다 득표자가 구속된다 | **동률 규칙**: 재투표 여부, 재투표할 때 후보(동률인 사람만 / 전체), 우선권을 가진 인물이 있는지 |
  | 엔딩 | 최종 투표 결과에 따라 달라지는 이야기를 보여 준다 | (엔딩 분기의 조건으로 정한다) |
  | 후일담 | 엔딩의 뒷이야기를 보여 준다. 엔딩 분기에 따라 달라지며 후일담의 적용 조건에 따라 인물마다 다를 수 있다(대체로 비슷하다) | (후일담 행의 조건으로 정한다) |
  | 전체 공개 | 게임 종료를 안내하고 **모든 단서와 모든 인물의 서사**를 볼 수 있게 한다 | 없음 |

  - **NPC 는 기본 틀에서 뺀다(사용자 결정)**: 플레이어 수가 캐릭터 수와 같아야 게임이 진행되고, NPC 여부의 동작은 기믹으로 처리한다(조사와 진행 순서가 NPC 여부에 따라 달라지는 것을 기본 틀에서 다루지 않기 위해서). **`인물.NPC` 컬럼은 유지한다**(NPC 를 쓰려는 제작자가 쓰도록). **`작품.최대인원` = 플레이어가 맡는 캐릭터 수**로 한다(사용자 확인 2026-10-17). 이미 그렇게 구현되어 있다: 인물을 만들거나 NPC 여부를 바꾸면 최대인원을 `max(NPC 가 아닌 인물 수, 1)` 로 다시 계산한다(`characters.py`, B5). 플레이어 수가 이 값과 같을 때만 시작하는 조건은 게임 시작 구현 때 만든다. **남은 미정**: 플레이어 수가 정확히 같아야 한다면 `최소인원`의 쓰임(지금은 최소 ≤ 최대 이면 어떤 값이든 허용).
  - **확인 필요**: 첫 투표에서 시간이 끝났는데 투표하지 않은 사람의 처리, 한도 없음일 때 진행 시간이 넘어가는 것을 화면에서 어떻게 보이는지. 자기소개 멘트를 줄지는 `소개` 컬럼이 비어 있는지로 판단하는지 카드 설정이 따로 있는지.
- **배역 선택은 진행단계 하나**다(보통 프롤로그 뒤, 게임마다 다름). 대기실에서 고르지 않는다.
- 시간 제어: 일시정지, 방장의 강제 넘기기를 지원한다. **제작자가 일시정지·넘기기를 금지하는 설정은 두지 않는다**(사용자 결정 2026-10-17, 앞서 정한 "페이즈 단위 금지"를 취소).
- **시간 종료와 진행(메모, 사용자 2026-10-17)**: 플레이 화면에서 ① 페이즈 시간이 끝나면 **자동으로 다음 단계로 진행**하거나 ② 시간이 끝나도 **방장이 "다음 단계" 버튼을 눌러야 진행**하도록 고를 수 있게 한다. 이 선택은 **방마다 방장이 정하며, 방 만들기 화면이 아니라 플레이 화면에서 한다**(사용자 정정 2026-10-17; 앞서 적은 작품별·제작자 설정이 아니다). 또 **시간 일시정지**와, 시간이 덜 되었어도 **방장이 먼저 진행**하는 것은 항상 가능하다(제작자가 금지할 수 없다).
- **"다 읽었다" 확인과 완료 현황(사용자, 2026-10-17)**: 내용을 읽는 단계(공통 스토리, 개인 서사, 엔딩, 후일담)에는 **"확인" 버튼**(이름은 사용자가 정함, 2026-10-17)을 두고, **전체 중 몇 명이 완료했는지** 보여 준다. 캐릭터 선택도 같아서 **고른 사람 수 / 전체**를 보여 준다. 완료를 눌러도 단계가 저절로 끝나는지는 확인 필요.
- **"확인"과 캐릭터 선택의 세부(사용자, 2026-10-17)**: 전원이 "확인"을 눌러도 **전원 완료만 표시**하고 단계는 저절로 끝나지 않는다(시간·방장·스크립트가 끝낸다). 캐릭터를 고른 뒤 바꾸는 것과 "확인"의 취소는 필요 없다. **공통 스토리 탭은 기본적으로 모든 단계에서 남는다.**
- **캐릭터 선택 미완료와 단계 종료(사용자, 2026-10-17)**: 시간이 끝났는데 캐릭터를 고르지 못한 사람이 있으면 **기다린다**(드문 경우). **진행단계의 끝은 기본적으로 엔진이 정한다**(시간 만료, 방장의 넘기기). **스크립트도 코드로 단계를 끝낼 수 있다**("가로챈다"는 시간·방장이 아니어도 스크립트가 특정 코드로 종료를 일으킬 수 있다는 뜻이라고 사용자가 설명함). **시간이 끝나도 방장이 넘기기 전에는 넘어가지 않는 것이 기본값**이라 캐릭터 선택의 기다림은 이것으로 충분하다(또는 캐릭터 선택 시간을 충분히 길게 준다). 단, **캐릭터 선택 카드만 "캐릭터 선택이 완료되어야 다음 단계로 진행할 수 있다"는 최소 조건**을 건다(방장의 권한을 막는 것이 아니라 최소 조건이며, 방장이 넘기려 하면 "캐릭터 선택이 완료되지 않았습니다."를 보여 준다, 사용자 2026-10-17). 이 조건 기능을 제작자에게도 열어 둘지는 미정.
- **방과 게임의 종료(사용자, 2026-10-17)**: 게임이 끝난 뒤 사람들이 방에 남아 이야기를 나누므로, 방장이 마침 버튼을 눌러야 종료되는 방식은 쓰지 않는다(방장이 먼저 나갈 수도 있다). **게임 종료는 전체 공개 단계가 시작될 때**이고, **방은 게임 종료 6시간 뒤에 종료된다.** 기존 자동 종료(`DB_RULES.md` B25: 대기 6시간, 진행 12시간 초과)는 **안전 상한으로 남긴다.**
- **게임 시작과 방장의 역할(사용자, 2026-10-17)**: 플레이어 수와 캐릭터 수가 같을 때 **방장이 시작 버튼을 누른다.** 방장이 플레이어가 아니면 **관전**한다(지금 구현은 방장이 "플레이어로 참여할지"의 둘 중 하나이고 관전 모드는 아직 없다).
- **관전 모드 두 가지(사용자 확정, 2026-10-17)**: 이름은 **GM 관전**과 **일반 관전**이다. 여기서 "GM"은 관전 모드의 이름일 뿐 **게임마스터라는 역할이 아니다.** 제작자가 나중에 자기 게임에 GM 역할을 넣을 수 있으므로 그 역할은 여기서 따로 정하지 않는다(이름이 겹치는 점은 인지하고 있다).
  - **GM 관전**: 플레이어들이 획득한 것과 개인에게 공개된 것(개인 서사 포함)을 모두 볼 수 있다. 아직 발견되지 않은 단서나 엔딩은 볼 수 없고 게임 흐름을 따라간다.
  - **일반 관전**: 개인 서사와 개인이 획득한 단서는 볼 수 없고, 공통으로 볼 수 있는 전체 공개 단서·공통 스토리 등만 본다. 누가 어떤 단서를 가져갔는지는 공개되는 경우에만 본다. 개인의 비공개 내용은 볼 수 없다.
  - 서버가 보는 사람의 종류(플레이어, GM 관전, 일반 관전)에 따라 보내는 내용을 거른다.
  - 관전자가 음성(Discord)으로 플레이어에게 아직 모르는 정보를 말해 줄 수 있는 한계는 알고 있다(사이트에서 막을 수 없다).
- **관전 설정 방식(사용자, 2026-10-17)**: **게임 시작 전에 방장이 설정**한다. 방에 들어온 사람을 **플레이 자리와 관전 자리로 구분**하는 식으로, 플레이어를 정할 때 관전도 할 수 있다. **자리는 방장이 지정할 수도 있고 본인이 조절할 수도 있다.** **방장 말고 다른 관전자도 들어올 수 있다.** 방 전체의 관전 설정을 조절할 수도 있고 **관전자마다 관전 모드를 조절**할 수도 있다. **방 전체 기본값은 일반 관전**이다. **게임이 시작된 뒤에 들어온 사람은 관전자가 되어 방 전체 관전 모드를 따른다.**
- **진행 권한과 이탈(사용자, 2026-10-17)**: 이탈한 사람의 자리(인물)는 이탈한 동안 유지한다. 진행 권한(다음 단계로 넘기기, 시간 일시정지 등)은 **방장이 기본**이다. **방장이 GM 관전이면 진행을 플레이어에게 넘기지 않고 직접 할 수 있고**, 일반 관전이면 플레이어 중 한 명이 진행 권한을 갖는다. 방장이 진행하지 않으면 **방에 들어온 순서대로** 플레이어가 갖는다. 권한을 가진 사람이 이탈하면 다음 순서 사람이 **임시로** 갖고, **원래 권한자가 돌아오면 권한이 돌아간다**(사용자 "맞아"를 이렇게 이해함). 방장은 진행 권한을 **특정 플레이어에게 직접 넘길 수도 있다.**
- **서버 재시작은 고려하지 않는다**(기존 결정, `HANDOFF_2026-10-14.md`). 진행 중인 게임이 재시작 뒤에 이어질 필요는 없다.
- 중간 이벤트는 `기믹적용`(기믹을 특정 페이즈에 붙임)으로 한다.
- **밀담**: 지금은 "밀담 가능" 안내만 하고 진행은 Discord 에서 한다. 나중에 채팅을 만든다(AI 테스트 플레이에도 필요).

### 1-2. 조사·단서·증언
- 조사 = 장소를 골라 그곳의 단서를 얻는다. 한 조사 페이즈에 1인당 2~5개.
- **기본 방식**: 라운드마다 모든 플레이어가 동시에 1개씩 고르고, 서버가 모아서 적용한다(순번 대기 없음). 순번제·자유 방식(최대 N개)은 설정으로 고른다.
- 같은 단서를 여럿이 고르면 **선착순**(사용자 결정. 네트워크가 빠른 쪽이 유리하다는 점은 짚어 두었다. **무작위로 정하는 방식은 쓰지 않는다**, 사용자 결정 2026-10-17).
- 단서는 대부분 **한 명만 보유**(선착순). 증언은 **여러 명이 각자 얻을 수 있고** 보여 주기·양도가 안 된다(들은 기억).
- 단서는 **양도**, **개인 공개**, **전체 공개**가 가능하다. 공개는 **취소**할 수 있다. **양도하면 그 단서에 걸린 공개는 사라진다**(소유권이 바뀌므로).
- 공개는 새 런타임 테이블로 기록한다(구상, 미생성): `번호`, `획득_번호`(FK→획득), `대상_참여_번호`(FK→참여, NULL 이면 전체), `공개일시`, `취소일시`. 공개가 유효 = 취소일시가 비어 있고 걸린 `획득` 행의 `보유여부`가 켜져 있음. `진행_번호` 컬럼은 같은 게임임을 DB 가 보장해야 할 때만 추가한다.

### 1-3. 투표와 질문
- 최종 투표의 기본은 **1표 비공개 동시 투표로 등장인물 중 한 명을 지목**한다. 개인 목표에 따라 실제 지목 대상이 달라질 수 있어도 행위는 같다.
- 투표 결과는 **엔딩 분기와 개인 목표 판정(후일담) 양쪽**에 쓰인다.
- 구분: 모든 플레이어가 동시에 선택해 **집계**하는 것은 `투표`, 한 사람의 답을 받는 질문(개인 지목)은 `기믹`.
- 질문의 답을 받는 것은 사이트 안의 선택만 해당한다(Discord 에서 말한 답은 사이트가 확인할 수 없다). "질문에 답했을 때" 이벤트는 두지 않는다.
- `인물.목표`는 자유 텍스트라 엔진이 달성 여부를 읽지 못한다. 목표에 따른 결과는 제작자가 `엔딩분기.조건`·`후일담.조건`에 구조화된 조건으로 적어야 한다.

### 1-4. 자유도와 언어
- 목표는 제작자가 원하는 기믹·트릭을 최대한 구현하는 높은 자유도이다.
- **어휘 조합(이벤트·조건·행동·변수)** + **자연어 입력(AI가 문법으로 번역)** + **제한된 게임 전용 스크립트 언어**를 모두 지원한다.
- 스크립트 문법은 **파이썬 문법을 따른다**. 변수·함수 이름에는 한글을 쓸 수 있다(파이썬이 허용). **한글 키워드판(번역본)은 만들지 않는다**(2026-10-15 결정, 아래 1-4-1).
- **실행은 우리 해석기가 한다.** 변환 결과를 실제 파이썬(`exec`/`eval`)으로 실행하지 않는다(안전 우선). 서버는 `ast` 로 읽기만 하고 허용한 구성 요소만 통과시킨 뒤 직접 해석한다.
- 제작자 코드는 자기 작품의 게임 상태만 만질 수 있고, 게임 API 로만 상태를 바꾼다.
- 4번(순서에 없던 페이즈로의 분기)과 5번(보는 사람마다 단서 내용이 다름)도 지원한다.
- **5번의 "지식"은 두 가지 출처가 모두 있다**: ① 인물의 직업·배경에 따른 사전 지식(소방관의 소방기구, 화학자의 약물 등), ② 게임 중 특정 경로로 얻은 지식.
- 완전히 새로운 화면과 장기적으로 3D 까지 구현하고 싶다(사용자 목표).

### 1-4-1. IR(내부 규칙 형식)과 편집기 (2026-10-15 결정)
- 개발은 **IR과 게임 엔진을 먼저**, 편집 방식(문법, AI)은 그 위에 하나씩 얹는다.
- **기믹의 본체는 스크립트**이다(이벤트-조건-행동 표 형식이 아니다). 높은 자유도가 목표이므로 반복·함수·변수 계산이 표현되어야 한다.
- **저장은 영어 키워드의 파이썬 형태 텍스트**로 한다. JSON 트리로 직렬화하지 않는다. `조건`/`결과` 같은 JSONB 컬럼에는 `{"형식버전": 1, "코드": "..."}` 정도의 봉투를 담는다(구체 형태는 미정).
- **한글 번역본(키워드를 한글로 바꾼 문법)은 만들지 않는다**(사용자 결정). 키워드만 바꿔도 콜론·들여쓰기·괄호 같은 구조는 그대로라 비전문가에게 직관적이지 않고, 전환 기능·이중 문서·예약어 충돌 같은 비용이 크다. 대신 **영어 키워드 단일 언어 + 한글 설명 보기 + 한글 도움말**로 간다.
- **한글 설명 보기**는 플랫폼이 코드를 읽어 **자동으로** 한글 문장으로 풀어 보여 주는 읽기 전용 화면이다(예: "플레이어가 '열쇠'를 가지고 있으면 / 플레이어에게서 '열쇠'를 회수한다 / 장소 '지하실'을 연다"). 제작자가 쓰는 것이 아니며 AI를 쓰지 않고 정해진 문장 틀로 만든다. **게임 명령어를 정의할 때 영어 이름·인자 형식·한글 문장 틀·한글 도움말을 한 세트로 정의**한다. 제작자가 직접 쓰는 설명은 `기믹.설명`에 선택으로 둔다.
- 저장이 영어이므로 나중에 수요가 생기면 한글 키워드 보기를 **보기 층으로 추가**할 수 있다. 번역어 표는 삭제했다(필요해지면 새로 만든다).
- **제작자가 지은 변수·함수 이름은 쓴 그대로** 보인다. 영문 별칭 기능은 두지 않는다(사용자 결정).
- 서버는 저장할 때 코드를 읽어 문법·API·이름 검사를 하고, 규칙이 참조하는 단서·장소 등을 함께 기록해 둔다(단서를 지울 때 영향 범위 확인용).
- 입력 방식: 직접 작성 / AI 프롬프트 복사 후 붙여넣기 / (블록은 **지금은 신경 쓰지 않음**, 사용자 결정). 블록은 코드를 만드는 방향은 쉽지만 임의의 코드를 블록으로 되돌리기는 어렵다.

### 1-4-2. 기믹의 시작 신호와 활성 조건 (2026-10-15)
- 페이즈 흐름의 분기는 **기믹**으로 한다("조건 A면 가 단계로, 아니면 나 단계로"). 진행단계는 모듈형이다.
- 기믹은 **언제 + 조건 + 행동**이고, 붙은 페이즈가 진행되는 동안 살아 있다. 시작 신호는 **사건형**(단서 획득, 투표 종료, 시간 경과 등)과 **상태형**("신뢰도가 70 이상이 되면")이 있다. 상태형은 참조하는 값이 바뀔 때 다시 확인한다.
- **판단 지점마다 선택 입력인 활성 조건 칸**을 둔다(비어 있으면 항상 활성): 장소 조사, 단서 획득, 양도·공개, 조합, 투표 참여, 진행단계 진입, 보여 줄 내용(사람마다 다름). 조건은 **플레이어마다** 따로 계산한다.
- **비활성일 때 이유를 보여 주지 않는다**(사용자 결정). 비활성은 회색으로 보이게 할지 숨길지를 장소마다 고른다.
- 힌트·안내는 **제작자가 기믹으로** 넣는다. 비활성 항목은 다른 비활성 항목과 똑같이 보이되 **클릭은 이벤트로 감지**해서 기믹이 반응할 수 있게 한다(사용자 결정). 숨김 항목은 화면에 없으므로 클릭이 없다. 서버는 클릭 대상이 그 플레이어에게 실제로 보이는 비활성 항목인지 확인하고, 이벤트 빈도를 제한해야 한다.
- 조사 후에 "조건 A를 만족한 후 다시 오세요" 같은 안내를 하는 사후 기믹도 있다(조사는 진행되고 횟수를 쓴다).
- 장소에서 단서를 얻으면 **그 장소가 비활성화되는 것이 기본**이다(`획득` 기록에서 계산할 수 있어 별도 상태는 필요 없다). 비활성화 범위(그 단서만 / 그 플레이어에게 장소 전체 / 모두에게 장소 전체 / 장소별 설정)는 미정.
- 비활성 항목을 누르는 클릭은 **조사 선택과 다른 종류의 이벤트**이고 조사 횟수를 쓰지 않는다. **그 항목을 고르는 화면이 열려 있는 동안에만** 받는다(장소는 조사 단계). 서버는 현재 페이즈와 대상이 보이는 비활성 항목인지 확인한다.
- **장소 비활성화 기본 규칙**(사용자): 남은 단서가 없으면 비활성이다(`획득` 기록에서 계산). 다른 플레이어가 먼저 골라서 비활성이 되는 경우도 대개 그 장소의 단서가 없어졌기 때문이므로 **"선점"은 별도 규칙이 아니라 소진으로 처리**한다. 따라서 소진된 장소는 다음 조사 페이즈에도 비활성이다. 단서가 여럿이면 여러 명이 조사할 수 있다.
- **일반 원칙(사용자)**: 이런 기본 규칙은 모두 **제작자가 자유롭게 바꿔 쓸 수 있어야** 한다. 플랫폼은 기본값을 제공하고, 제작자는 활성 조건과 기믹으로 덮어쓴다.
- **조사 선택의 반영 방식(사용자 결정)**: 제작자가 고를 수 있고 **기본은 바로 반영**이다. 한 사람이 장소를 고르면 서버가 즉시 처리하고, 아직 고르는 중인 다른 플레이어 화면에서도 그 장소가 바로 비활성으로 바뀐다. 같은 순간에 눌러서 진 사람은 횟수를 쓰지 않고 다시 고른다(서버에 먼저 도착한 요청이 이긴다). 기본 방식에는 **실시간 연결(서버가 화면을 즉시 갱신)** 이 필요하다.
- 선택 방식 중 **모아서 한꺼번에 반영**하는 방식(모두 고른 뒤 한 번에 처리)도 제작자가 고를 수 있다. 이때 겹침의 승패는 선착순이 아니라 **캐릭터 우선순위 등 제작자가 정한 요소**로 정한다(사용자). 앞서 적은 "겹치면 선착순"은 기본(바로 반영)의 서버 도착 순서에만 해당한다.
- 큰 장소 안에 탐색할 곳이 여럿이면 `장소.상위_장소_순서`로 표현한다. 조사 단위는 가장 안쪽 장소이고, 바깥 장소는 안쪽 장소가 남아 있는 동안 활성으로 본다.
- **행동 전에 끼어들어 막거나 바꾸는 이벤트**: 서로 모르는 기믹끼리 조합(독살+해독제)하게 해 주는 장치이다. 사용자 의견은 "자유도를 높이는 것이라면 OK"이므로 **지원하는 방향으로 기록**한다. 구현 시점은 엔진을 만들 때 정한다. 설계 원칙: 엔진의 모든 기본 동작(조사, 공개, 양도 등)이 **하나의 처리 경로**를 거치게 해서 "행동 전" 시점을 나중에 추가할 수 있게 한다.
- 정해야 할 규칙: 조건이 참인 동안 반복할지 한 번만 실행할지(기본은 한 번 제안), 여러 기믹이 동시에 발동할 때의 순서, 기믹이 기믹을 부르는 연쇄의 상한.

### 1-4-3. 공통 스토리와 열람 자료 (2026-10-15)
- 플레이어는 플레이 중 언제든 **'공통 스토리'·'개인 서사' 탭**을 눌러 내용을 다시 읽을 수 있다(사용자가 아는 다른 서비스의 방식). 어떤 탭을 보일지는 DB 컬럼이 아니라 **플레이 화면 설정**(제작자 테마와 같은 곳, 저장 형식 미정)에서 정한다.
- **공통 스토리는 `작품.공통스토리`**(TEXT, 비어 있을 수 있음, `0013`)에 둔다. 개인 서사는 `인물.서사`에 그대로 둔다(옮기지 않음). 진행단계는 공용·불변 행이라 작품별 글을 담을 수 없다.
- 다른 단계에서 필요한 서사는 **기믹**으로 처리한다. 지도 같은 이미지는 `미디어`.
- 글을 따로 저장하는 **`자료` 테이블**을 만들었다(`0014`): 번호, 작품_번호, 순서, 제목(필수), 내용(필수). 기믹이 긴 글을 번호로 불러 쓰고 여러 기믹이 재사용한다. 제작자는 `작품.계정_번호`로 알 수 있어 계정 컬럼은 두지 않았다(사용자 구상의 `계정_번호`는 제작자 표시 용도라 중복이므로 제외, 공동 제작·공유 때 추가). 기믹이 글을 불러오는 명령은 게임 명령어를 정할 때 정한다.

### 1-4-3-1. 페이즈 이름·탭 유지·카드 설정 (2026-10-16 결정)
- 제작 화면은 **카드를 칸에 놓는 흐름 중심**이다. 칸 = `진행순서`(페이즈), 카드 = `진행단계`(`진행구성`으로 칸에 놓음). 카드를 사이에 끼워 넣으면 뒤가 밀린다(서버가 칸의 내용을 옮김, `docs/DB_RULES.md` B34).
- **플레이어에게 무엇을 보낼지는 제작자가 정하고 서버에 요청**한다. 서버는 요청을 실행하는 쪽이다. 별도 "플레이어용 내용" 테이블은 두지 않는다.
- **탭(예: 개인 서사)을 다음 페이즈에도 남길지는 제작자가 고른다.** 기본은 **남는다**. 가끔 사라져야 하는 탭이 있다(예: 개인 서사를 더 읽지 못하는 테마). 이 선택은 카드를 놓는 자리의 `진행구성.설정`에 담는다(JSONB 내부 구조는 엔진 설계에서 정함).
- 페이즈 이름(`진행순서.이름`)은 제작자가 정하고, 같은 카드가 한 작품에 둘 이상이면 카드 표시 이름은 "1차 ○○"·"2차 ○○"(칸 위치 순서, 저장하지 않고 계산)이다. 스크립트는 번호가 아니라 이름으로 가리킨다.
- 자유 연결(카드끼리 임의로 잇기)은 보류했다. 범위는 카드 흐름 + 카드·기믹의 세부 설정까지이다.

### 1-4-4. 사람마다 다른 단서 내용 (2026-10-15)
- **단서는 기본 내용 하나만** 가진다(일반 단서). 지식·인물에 따라 다르게 보여야 하는 **소수의 경우만 기믹이 보충**한다(사용자). 단서 테이블에 변형 칸이나 변형 테이블을 따로 두지 않는다.
- 다른 글은 `자료` 테이블에 둔다(예: "단서 5 - 소방관 시점"). 기믹 행동 어휘에 "이 플레이어에게 이 단서를 이 글로 보여 준다"를 넣고, 플레이어별로 어떤 글을 보고 있는지는 런타임 상태로 기억한다(저장 방식은 게임 상태 모델을 정리할 때 결정).
- 변형은 그 플레이어에게만 적용된다. 공개받는 쪽은 받는 사람 기준으로 계산한다. 지식을 나중에 얻으면 "지식 태그를 얻었을 때" 상태형 기믹이 내용을 바꾼다.
- 변형이 많은 작품의 부담은 공통 라이브러리 기믹("지식에 따라 단서 내용 바꾸기")으로 줄인다. 단서 편집 화면의 "변형 있음" 표시는 코드 저장 시 뽑아 둔 참조 정보로 만든다.
- 지식은 이름 붙은 태그로 보고, 인물의 처음 태그 + 게임 중 얻은 태그로 판정한다(제안).

### 1-4-5. 진행단계의 형태와 플레이 화면 (2026-10-17 대화, 사용자 선택)
- **진행단계와 기믹 모두 스크립트와 해석기로 만든다**(사용자: 제작자가 원하는 단계를 원하는 코드로 짜게 하는 것이 목표). 기본 진행단계 11개도 서버 코드가 아니라 같은 스크립트로 쓴다. 서버 코드로 남는 것은 스크립트가 부르는 **기본 명령(부품)** 이다(단서 주기, 장소 닫기, 표 기록, 타이머, 동시 선택 모으기, 페이즈 넘기기 등). 11개를 스크립트로 써 보면서 꼭 필요한 부품을 추려 **명령 목록의 최소 범위**를 정한다.
- **플레이 화면은 블록 조합 방식(B)으로 간다**(사용자 선택). 개발자가 기본 블록(글, 이미지·영상, 선택지 목록, 카드 목록, 입력칸, 타이머, 현황표, 버튼 등)을 만들고, 제작자는 스크립트로 이를 조합하며 **조합한 것을 새 블록으로 정의**할 수 있다. 제작자가 HTML·CSS·JS 를 직접 쓰는 방식(C)은 택하지 않았다(안전 검사·모바일 대응 부담).
- 이 선택의 한계: 제작자가 조합할 수 있는 것은 **기본 블록이 얼마나 세밀한가**가 정한다. 기본 블록이 큰 덩어리(선택지 목록, 현황표 등)뿐이면 만들기 쉽고 모바일 대응도 쉽지만 조합으로 만들 수 있는 것이 적다. 작은 재료(글, 이미지, 도형, 이미지 위 좌표 배치, 클릭 영역, 입력칸 등)까지 있으면 "지도 위 핀을 눌러 고르기" 같은 것도 조합으로 만들 수 있지만 조립할 양이 늘고 화면 크기별 배치 규칙이 필요하다. 재료로 없는 것만 개발자가 기본 블록을 더 만들어야 한다. 복합 블록의 배치 규칙은 제한을 둔다(상세 미정).
- **미정**: 기본 블록의 세밀함(큰 덩어리 vs 작은 재료)과 최종 목록, 복합 블록을 담는 형식, 스크립트가 화면과 주고받는 약속(내 상태 받기·입력 제출), 새 블록을 만드는 편집 화면. 11개 진행단계를 스크립트로 쓰면서 확인한다.

### 1-4-6. 개인 서사의 부분 공개 (2026-10-17 논의, 사용자 선택)
- 서사의 일부를 따로(시점·인물별로 다르게) 공개하려면 **부분을 독립적으로 가리킬 수 있어야** 한다. 저장하는 컬럼 수보다 이것이 핵심이다. 스크립트(기믹·진행단계를 직접 만들 때)가 가리킬 수 있도록 **부분마다 고유 ID**를 둔다. 제작자는 기믹·진행단계를 직접 만들 때가 아니면 ID 를 알 필요가 없다.
- **저장은 `인물.서사` 컬럼 하나를 유지한다**(사용자 선택). 글 안에 부분의 시작과 고유 ID를 알리는 표기를 넣는다. 표기 문법은 미정(설명용 예: `[부분: s_b2]`).
- **제작 화면**: 서사를 입력하는 곳에서 "서사 추가하기" 버튼을 누르면 아래에 새 텍스트창이 생기고(서사 2, 3 …) 새 고유 ID가 만들어진다. 저장할 때 ID와 구분 표기를 넣어 컬럼 하나로 합치고, 다시 열면 해석해 여러 텍스트창으로 복원한다. 제작자는 ID나 문법을 직접 쓰지 않고 화면에는 "서사 1·2"로 보인다.
- **공개 방식(사용자 결정, 2026-10-17)**: 프로필 숙지 카드마다 **보여 줄 서사를 고른다**(캐릭터별, 복수 선택, 기본값은 서사 1). 같은 카드를 페이즈에 한 번 더 놓으면(2차 프로필 숙지) 거기서 다시 고른다. **개인 서사 탭에는 가장 최근 프로필 숙지 카드가 고른 서사가 보인다**(누적이 아니라 교체): 2차 카드가 서사 2만 고르면 서사 1은 사라지고 2가 보이며, 서사 1·2를 고르면 서사 1 뒤에 2가 이어서 보인다. 선택은 카드를 놓은 자리의 `진행구성.설정`에 담는다. **카드마다 캐릭터별로 보여 줄 서사를 고른다**(사용자 정정, 2026-10-17 — 앞서 "모든 인물에게 같은 번호"로 적은 것을 대체). 기본값은 각 캐릭터의 서사 1이다. 현재 보일 서사는 흐름에서 지금까지 놓인 마지막 프로필 숙지 카드로 계산할 수 있어 공개 상태를 따로 저장하지 않는다. 사건(단서 획득 등)을 기준으로 하는 공개는 기믹이 맡는다.
- **서사 부분의 개수와 표기(사용자, 2026-10-17)**: **인물당 서사는 최대 5개**로 한다. 부분 표기는 **매우 흔치 않은 문자열**이고 아래와 같이 **확정**했다(사용자 2026-10-17): 한 줄이 `@@MMPART:` + 영소문자·숫자 6자(ID) + `@@` 이다(앞뒤 공백은 무시하고 줄 전체가 이 모양일 때 표기). ID 는 서버가 무작위로 만들고 한 인물 안에서 겹치면 다시 만든다. 본문 어느 줄에든 `@@MMPART:` 글자가 들어 있으면 저장을 거부한다. 서버가 부분 목록(ID, 본문)을 받아 글로 합쳐 저장하고 화면은 표기를 보지 않는다. 맨 앞에 표기가 없는 옛 서사는 부분 하나로 보고 다음 저장 때 ID 를 붙인다. 저장할 때 줄바꿈을 하나로 맞추고 각 부분 앞뒤의 빈 줄을 지우며, 빈 부분은 거부한다. 확정 스냅샷에는 확정할 때 해석한 부분 목록(ID, 본문)을 담는다. **글자 수는 서사 전체 10000자**로 하고(지금은 5000자이며 앱 코드의 제한이고 DB 제약은 없다), **서사를 나눌 때마다 부분 하나의 제한이 줄어든다**(10000자를 부분 수로 나눠 소수는 버림): 1개 10000자, 2개 각 5000자, 3개 각 3333자, 4개 각 2500자, 5개 각 2000자. 결과적으로 전체 합은 항상 10000자 이하이다. 부분이 늘면 기존 부분이 새 제한을 넘을 수 있으므로 **"서사 추가하기"를 누르기 전에 편집기가 알린다**(사용자 결정 2026-10-17). 부분 길이를 균등하게 묶는 방식이고, 합 안에서 부분마다 자유롭게 나누는 것은 허용하지 않는다(알고 있음).
- **서버**: 플레이어에게는 공개가 허용된 부분만 내려 준다(비공개 부분이 브라우저로 새면 안 된다). 부분 목록은 서버의 한 곳에서만 해석한다.
- 확정 스냅샷에는 원문이 아니라 **확정할 때 해석한 부분 목록(ID·본문)** 을 담는 쪽이 낫다(해석 규칙을 나중에 고쳐도 과거 작품이 달라지지 않는다). 미결정.
- **미정**: 표기 문법과 본문 속 같은 표기 처리, 잘못된 표기 검사(편집기와 서버 양쪽), 기존 표기 없는 서사의 처리, ID 중복·삭제 시 참조 검사, 스크립트가 ID 를 쓸 때 제작자·AI 에게 ID 를 보여 주는 방법, 선택한 서사 번호가 인물의 서사 수를 넘거나 서사를 지워 번호가 밀릴 때의 경고(저장 시 검사), 인물에게 선택한 번호의 서사가 없을 때 보이는 것, 같은 페이즈에 프로필 숙지 카드가 둘일 때의 우선순위, 선택한 서사들을 이어 보이는 순서(서사 번호 순 제안).

## 1-6. 참고 자료: 쏘빅 제작 화면 (사용자 제공 스크린샷, 2026-10-15)
화면에서 보이는 범위만 기록한다(직접 써 본 것이 아님). 범용 모임·게임 플랫폼처럼 보이며 머더미스터리 전용인 우리와 범위가 다르다. **사용자: 참고용일 뿐이며 모방하지 않는다**(모방이 방법으로는 좋아도 원하는 방식이 아님). 제작 화면의 틀은 이 구조를 따르지 않고 별도로 정한다. 디자인은 따라 하지 않고 구조와 기능만 참고한다.
- 구조: 편집 모드/진행 모드 전환, 미리보기 패널, 타이머. **덱 리스트**(덱 = 시간 단위 화면)의 각 덱에 시간·자동 전환·첫 덱 복귀·선고정덱/후고정덱·비디오·오디오 설정이 있고, 덱 안에 **모듈**이 목록으로 들어간다.
- 기본 모듈: 텍스트, 설문, 투표, 미니게임, 자리배치, 가중치, 밸런스, 쪽지, 채팅, 음성 채팅, 매칭, 입력폼, 관계도, 정보, QR 코드, 함수 블록, 점수판, 인벤토리, 참가 관리, 커맨더, 게임 설정, 에이전트, 티어 메이커. 모듈마다 오른쪽에 **전용 설정 패널**(모듈 설정/접근 권한, 표시할 플레이어 필터 등)이 열린다.
- 대응: 덱 ≈ `진행순서`, 모듈 ≈ `진행구성`의 진행단계, 모듈 목록 ≈ 공통 진행단계·기믹 라이브러리, 모듈별 설정 패널 ≈ 사용처별 설정 칸(`진행구성`·`기믹적용`에 필요), 함수 블록·커맨더 ≈ 스크립트·기믹, 미리보기 ≈ 한글 설명 보기·모의 실행. 우리 스키마가 이미 같은 모양이다.
- 공통 라이브러리 후보: 쪽지, 설문, 점수판, 인벤토리, 관계도(`관계` 테이블 있음). 음성 채팅은 우리가 Discord 를 쓰므로 해당하지 않는다.

## 1-7. 제작 화면 원칙 (2026-10-15)
- **제작 순서는 자유**여야 한다(사용자). 사람마다 제작 순서가 다르므로 정해진 단계를 따라가는 방식이 아니라 **빈 작업 공간을 만들고 원하는 것부터 채우는** 방식이다. 이름조차 나중에 정하거나 바꾸는 경우가 있다.
- 쏘빅 제작 툴의 장점을 어느 정도 배운다(모방은 하지 않음).
- 영향: 작품·인물 등을 이름 없이 먼저 만들 수 있어야 하고(자동 임시 이름 또는 이름 칸 선택 입력), 완성도 검증은 만드는 도중이 아니라 **확정 전**에 한다. 이름을 나중에 바꿔도 참조가 깨지지 않아야 한다(콘텐츠 테이블은 이미 `순서` 번호로 참조하므로 안전). 라이브러리 항목(`진행단계`·`기믹`)은 이름이 계열 식별자라 이름 변경이 새 계열이 되는 점을 다시 검토해야 한다.
- **결정(사용자, 2026-10-15)**: 작품 제목·인물 이름 등은 자동 임시 이름을 만들지 않고 "나중에 바꿀 수 있다"는 안내만 한다(인물 이름은 겹쳐도 된다). **라이브러리의 계열 전체 이름 변경을 허용한다**(한 번에 모든 버전의 이름을 바꾸고, 같은 이름의 계열이 이미 있으면 거부). 이를 위해 `0015` 가 불변 트리거에서 `이름`도 예외로 뒀다.
- **재검토 필요(사용자, 2026-10-15)**: 아래 구현은 DB 테이블마다 양식을 붙인 것이라 의도한 "제작자가 요소를 독립적으로 만들고 연결하며 새 규칙·기믹까지 정의하는 제작 환경"과 다르다. 편집기 구조는 `EDITOR_DESIGN.md` 에서 다시 설계한다.
- **구현(작업공간, 2026-10-15, 재검토 대상)**: 작품 화면은 탭(개요 / 장소·단서 / 사건 / 관계·자료 / 진행 / 결말 / 확정)이고 어느 탭부터 채워도 된다. 콘텐츠 항목은 `backend/app/content.py` 의 명세 하나로 API 와 입력 양식(`GET /api/content/schema`)을 함께 만든다. 진행 탭은 페이즈를 만들고 라이브러리의 진행단계·기믹을 붙이며(삭제된 항목은 '삭제된 항목'으로 표시), 확정 탭이 확정 검사·스냅샷·버전 목록을 맡는다(`confirm.py`). 라이브러리 화면은 `/library`. **아직 없음**(페이즈 끼워 넣기·옮기기는 2026-10-16 구현): 미디어 업로드, 규칙·조건의 구조화 입력(지금은 JSON 직접 입력)·한글 설명 보기·모의 실행.

## 1-8. 실시간 전달의 설계 요건 (2026-10-17, 전달 방식은 미결정)

기존 결정(`HANDOFF_2026-10-14.md`): 폴링(2~3초)으로 시작하고 필요하면 SSE 로 교체, 웹소켓은 쓰지 않는다. **결정(사용자, 2026-10-17): 처음부터 SSE** 로 간다(서버 → 화면은 SSE, 화면 → 서버는 일반 요청). 기존의 "폴링으로 시작"을 바꾼 것이다. 아래 요건 중 앞의 다섯 가지는 SSE 든 폴링이든 필요하다.
- 플레이어의 행동은 일반 요청(POST)으로 보내고, 화면은 **상태 조회**로 최신 상태를 가져온다. 실시간 알림이 있더라도 "바뀌었으니 다시 조회하라"는 신호 역할만 한다(알림을 놓쳐도 조회로 복구된다).
- 상태에 **버전 번호**를 붙여, 늦게 도착한 오래된 응답이 최신 화면을 덮어쓰지 않게 한다. 연결·재연결 때는 먼저 최신 상태를 조회한다. 알림 연결을 쓰더라도 느린 주기의 조회를 안전망으로 둔다.
- 상태 조회가 돌려주는 내용은 **그 사람(플레이어, GM 관전, 일반 관전)에게 허용된 범위**로만 한정한다.
- **연결 끊김과 실제 이탈은 다르다.** 끊긴 뒤 일정 시간(유예)이 지나야 이탈로 본다(대기실의 `member_timeout` 과 같은 생각). 정상 종료와 갑작스러운 끊김을 구분한다.
- **타이머**는 서버가 종료 예정 시각과 서버 기준 시각을 보내고 화면이 남은 시간을 계산한다. 일시정지·재개·종료 같은 변화만 알리고, **시간 만료 판정은 서버가** 한다(서버 프로세스는 하나).
- **SSE 연결의 인증: `fetch` 로 스트림을 읽고 기존 `Authorization: Bearer` 토큰과 `로그인세션` 검증을 유지한다**(**잠정**, 2026-10-17: 사용자가 GPT 와 Claude 의 의견을 들어 보는 중이고, 둘 다 이 방식을 권해 "그래도 될 것 같다"고 함. 확정하면 이 표시를 지운다). 브라우저 기본 `EventSource` 는 헤더를 보낼 수 없고 끊기면 자동으로 다시 연결하므로 쓰지 않는다. `fetch` 방식에서는 다음을 직접 구현한다: ① 데이터가 중간에 잘리거나 여러 메시지가 붙어 와도 올바르게 나누는 SSE 메시지 해석 ② 재시도 간격을 늘리는 재연결 ③ 연결·재연결 뒤의 최신 상태 조회와 오래된 응답의 덮어쓰기 방지 ④ 인증 실패 때는 무한 재시도하지 않고 로그인 필요 상태로 전환 ⑤ 방을 옮기거나 나갈 때 기존 연결을 끊고 중복 연결을 막는다.
- 모바일은 "연결이 계속 유지되는가"가 아니라 **"끊겨도 복구되는가"** 를 기준으로 설계한다(화면 꺼짐·앱 전환으로 연결이 끊긴다는 전제). 연결이 막히지 않는지(프록시 버퍼링)는 실제로 시험해야 한다. 쿠키 인증은 지금 선택할 이유가 없어 쓰지 않는다(쿠키 보안 설정과 CSRF 대응 검토가 필요하다).

## 1-9. 스크립트의 입력 대기와 재개 (2026-10-17, 사용자 결정: A2)

- **실행 상태를 데이터로 관리하되, 첫 구현에서는 서버 메모리에 보관한다**(A2). 실행 위치, 변수, 기다리는 대상을 별도 데이터로 들고 있다가 입력이 오면 이어서 실행한다. 비동기 작업을 멈춰 두는 방식(A1)은 쓰지 않는다. 이유: 지금 백엔드가 동기 방식(`psycopg` 동기 연결 풀, 일반 `def` 엔드포인트)이라 A1 은 이벤트 루프와 동기 DB 호출을 잇는 장치가 필요하고, A2 는 요청이 올 때마다 해석기를 한 단계씩 실행하면 되어 그대로 맞는다. 상태를 확인·시험하기 쉽고 나중에 DB 저장을 붙일 수 있다. 서버 재시작 복구는 하지 않는다(기존 결정). 해석기를 처음부터 "단계를 나눠서 실행하는 구조"로 설계해야 하는 부담은 감수한다.
- 어느 방식이든 처음부터 필요한 것: ① SSE 연결과 스크립트 대기를 분리한다(연결이 끊겨도 스크립트는 계속 기다린다). ② 대기 중인 질문에 고유 ID 를 둔다(재접속 때 같은 질문 복원, 중복 제출·이전 질문의 답은 걸러낸다). ③ 시간 종료·페이즈 전환·방 종료 때 대기를 끝내는 규칙을 정한다. ④ 기다리는 동안 DB 연결과 잠금을 붙잡지 않는다.
- 스크립트에서 입력을 기다리는 문장은 **순서대로 읽히는 모양**("선택 = 기다리기(...)")으로 한다. 그러면 나중에 구현 방식이 바뀌어도 제작자의 스크립트는 바뀌지 않는다. 문법은 0-6 에서 정한다.

## 2. 제안 (사용자 미확정)
- 자연어 → AI 가 영어 키워드 스크립트로 변환 → 파서가 검증(오류 시 재시도) → 제작자가 한글 설명 보기로 읽고 확인 → 내부 규칙 형식(IR)으로 저장. 고급 사용자는 문법을 직접 쓴다.
- AI 비용: 제작자가 자기 AI 챗에서 만들어 붙여넣기(+문법 설명서·작품 정보 복사 버튼)와 AI 없는 문법·블록으로 시작하고, API 키 연결이나 플랫폼 부담은 나중에. AI 호출부는 "텍스트를 받아 문법 텍스트를 돌려주는 모듈"로 분리해 둔다.
- 화면: **서버가 화면을 설명하고(JSON), 클라이언트는 고정 부품으로 그린다.** 기본 화면은 고정, 기믹이 띄우는 선택창·입력창·안내문, 이후 부품 조합 화면, 장기적으로 3D 장면(데이터 기술) → 마지막에 격리된 사용자 정의 화면. 화면 설명에 `종류` 값을 두어 확장 가능하게 하고, 화면 입력은 하나의 이벤트 형식으로 통일한다.
- 지식은 **이름 붙은 태그**(소방, 약물 등)로 보고, 인물이 처음부터 가진 태그 + 게임 중 기믹이 추가하는 태그의 합으로 판정한다(단서마다 인물별 관계를 적는 것보다 확장하기 쉽다고 판단).
